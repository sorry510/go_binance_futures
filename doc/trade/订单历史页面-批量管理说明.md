# 订单历史页面：按筛选条件物理删除与人工状态修改（Schema v24）

> 更新时间：2026-11-09。项目分支 `feat/trade-upgrade`。本文件说明**本地开发代码**，不是已部署生产环境的功能确认。

## 一、删除流程

页面：**合约交易 → 合约订单**。

按账户、Owner、币种模糊匹配、LONG/SHORT、系统持仓状态、结算状态及开仓时间筛选，点击**批量删除筛选结果**。前端重新读取服务端实际命中总数，弹出一次二次确认；确认后提交 `POST /orders/batch/delete`，携带完整过滤条件和 `expected_count`。无需填写操作原因、不再输入 `DELETE N`，也没有「隐藏/恢复」功能。

批量删除针对**全部匹配周期，不是当前分页**。服务端在事务内重新选择该账户的周期；若数量变化，返回 HTTP 409，让页面刷新后重新确认。每次最多 **5000 个周期**；超限应缩小搜索范围。

### 实际删除的数据

针对每个符合安全条件的 `account_id + position_id`，事务按以下顺序删除：

1. `futures_trade_fills`：归属于该周期的逐笔真实成交；
2. `futures_managed_orders`：该周期关联的 OPEN/CLOSE/TP/SL Managed 子订单；
3. `futures_ownership_adjustments`：该周期人工归属调整记录；
4. `order_history_admin_audits`：该周期人工展示状态修改记录；
5. `futures_managed_positions`：主仓位周期。

以上操作属于**不可恢复的物理删除**，不保留隐藏副本。**不删除 `futures_orders` 交易所实时镜像、全局的配置与风控记录、其他账户或其他周期的数据**。真实交易所历史本身不受本地数据库删除操作影响。

### 防止影响正在运行的交易

批量删除必须满足每一个命中周期都符合以下条件，否则**整个批次拒绝，不做部分删除**：

- `status=closed`、`managed_qty=0` 且有明确 `closed_at`；
- `settlement_status` 为 `settled` 或 `legacy`，不能删除正在等待成交补录、未完成结算与风控处理的 `incomplete`；
- 所有关联 Managed 订单均无 `pending/submitted/partially_filled/reconcile_required`，避免遗漏未撤销的保护单；
- 结束时间以及真实 Fill 的最新 `trade_time` 均早于当前时间 **30 天**。最近平仓 Fill 参与交易冷却，不能在冷却期间物理删除；
- 服务器在 MySQL/InnoDB 事务中锁定候选仓位，再核实上述条件；任意 SQL 失败则完整回滚。

**边界**：永久删除会改变历史报表/审计记录。上述约束旨在不破坏**当前交易执行、保护单、待结算风控及近期选币冷却**，并不代表可以恢复已删除的历史数据。旧周期若仍被其他业务留作追溯，删除后也不会出现在本系统历史查询中。

## 二、手动修改持仓状态和数据完整性

原来的**批量修改状态 / 完整性**功能保留。该操作仍然只修改**历史页面展示字段**，不修改真实交易系统的 `status`、`settlement_status`、持仓、Fill 或自动风控：

- `history_status_override`：页面显示状态；
- `history_completeness_override`：人工标记待核对 / 进行中 / 人工已检查，不允许冒充 `verified`；
- `history_modified_at`：手动状态修改时间；
- `order_history_admin_audits`：人工修改审计，记录操作者、原因和变更前后值。

可清除人工标注，恢复系统从真实成交与结算计算的完整性。账户级 T0 的收益认证规则不变。

主表列顺序仍为：**持仓状态 → 已核实净交易盈亏 → 名义收益率 → 数据完整性**。

## 三、接口

| 接口 | 作用 |
| --- | --- |
| `GET /orders` | 新版持仓周期分页列表，按账户过滤 |
| `GET /orders/:position_id/details` | 关联 Managed 订单与真实 Fill 明细 |
| `POST /orders/batch/delete` | **物理删除**完整筛选范围内符合安全门禁的结束周期及关联数据，需 `expected_count` |
| `POST /orders/batch/preview` + `POST /orders/batch/apply` | 保留，仅用于**人工展示状态和完整性**批量修改 |
| 旧 `DELETE /orders` / `DELETE /orders/:id` | 仍是 HTTP 410，防止旧客户端绕过确认及终态检查 |

所有新接口仍要求后台 JWT 登录；账户 `main` 与 `lead` 严格分离。
