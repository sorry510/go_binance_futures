## 一、实际新增的代码（本轮完成）

- `service/spotstrategy/s3_legacy_preflight.go` 新增 `InspectLegacySpotRisk(ctx, db, client)`：**不写数据库**，仅读取传入数据库的 `config` 当前模式、`spot_strategy_orders`、`spot_strategy_holdings`；从传入的 Spot `Client` **只调用** `Balances(ctx, main)` 和 `OpenOrders(ctx, main, "")`，即账户级全部币种余额/挂单而不是某一个 BTCUSDT 的结果。
- 查询时同时识别 `main/auto_strategy` 内部未终结状态、其他 Owner 的本地订单与 Holding、外部未知挂单、本地已终结但交易所仍为 OPEN、同 ClientOrderID 不同交易所 orderId、非法 OpenOrders 状态、Spot 非法余额和失败的私有查询。通过本地唯一 ID 比较，不把外部手工订单挪入本地策略所有权。
- 返回 `LegacyPreflight`：`observed_at`、`mode`、`read_complete`、`ready_for_live`、`evidence_source`、`balances/open_orders/local_pending/holdings` 和**稳定去重** `blockers`。**每次 `ready_for_live=false`**；没有审计员身份、旧仓所有权和独立授权机制，单次快照绝不放行实盘。
- 访问 DB 或 SDK 失败时返回 `ErrReconciliation`、`read_complete=false`；**错误不能退化为「空仓位安全」**。所有金额使用精确十进制输入，不通过 float 比较。
- 本轮**没有**连接定时调度，也没有添加 HTTP 一键激活接口。未自动调用真实 Binance API、生产数据库或订单接口；正式接入将需要经过身份权限和敏感账户数据访问审查。
- `service/spotstrategy/s3_legacy_preflight_test.go`：9 项隔离 SQLite+Fake 用例，覆盖干净空账户仍不放行、其他账户资产和挂单、已归属与 ID 冲突、旧 Holding/模式直改、REST 读取失败、禁止额外下单/撤单、其他 Owner、本地/交易所重复和非法 OPEN 状态，以及伪造 `ready_for_live=true` 的结构体不能授予真实交易许可。**隔离 Fixture，不是交易所证据**。

### 当前只读预检的固有限制

1. 现货账户没有原生的仓位「开/平」所有权：余额只能说明资产存在，不能证明它来自旧自动订单还是手工订单。所有非零账户资产按“待确认所有权”处理；即使余额为 0，历史 SELL 保护任务和旧单仍不能证明全部已关闭。
2. Binance 客户端签名证明是**本次请求由客户端签名**，不是交易所为每一份 REST JSON 响应作数字签名。这里的 `evidence_source=unattested_readonly_snapshot` 是事实标签，不能把 Fake 或代理响应称为已核实。
3. 旧现货逻辑没有完整可靠的订单/Fill 所有权数据表，不允许凭新 `spot_strategy_orders` 的空集合推断旧系统不存在未结风险。
4. 真实部署、数据库结构、老任务仍存活等**完全没有检查或更改**。本阶段不提供清空、认领、撤单或直接 `mode=strategy` 的修改动作。

## 二、后续持久化授权审计（待实现，建议 Schema v26）

新增的正式审计必须独立于已有 v25 金融表；**不能向现有 v25 `CREATE TABLE IF NOT EXISTS` SQL 里偷加新表并当作已迁移**。待用户批准数据库版本升级/单独 Review 后，通过唯一合法的 `./go_binance_futures sync db` 实施幂等的 v25→v26 迁移，生产迁移需另外授权。建议新表 `spot_strategy_authorization_events`，且不覆盖订单/Fill 表：

- 事件类型：`review_requested`、`preflight_observed`、`review_rejected`、`grant_issued`、`grant_revoked`、`grant_expired`。**先只实现读取/拒绝审计，再开放任何 grant；不能把「请求」等同「批准」**。
- 必须字段：唯一事件 ID、严格绑定的当前登录 operator ID / 角色与授权来源、请求幂等键、`main/auto_strategy`、模式变更 old→requested、批准的符号集合与 quote 预算、原始只读证据摘要/原始快照安全存储位置、快照捕获时间/过期时间、操作者确认的旧 SELL/库存处置说明、创建时间、撤销原因。
- 数据完整性：APPEND ONLY 事件流 + 唯一幂等键 + 稳定行锁和单调序列 + 前一事件哈希关联。哈希链是**防止非授权修改的检测手段**，不是独立的可信签名；缺少外部不可修改锚或数据库权限隔离，具有 DB 管理权限的人仍可重写整条链。应加只读查询、权限隔离与外部审计/备份锚。
- Grant 有明确作用域、失效时间、单独撤销、登录身份权限和二次确认。一个 Grant **不可以跨币、跨账户、无限延期或在进程重启时推断恢复**。不允许通过 HTTP 普通 JWT Username 或环境变量字符串直接授予实盘。
- 真实交易写入前，即使已有 Grant，也必须再读取最新有效授权、符号配置和额度、当前 mode、账户/挂单/余额最新对账、具备可审计来源的 `myTrades`，在 Binance SDK 实际 POST/DELETE **现场二次验权**。有任意缺口即保持 `ErrLiveWriteDisabled`；不能只在 Runner 启动前检查一次。
- 迁移测试：独立 SQLite 建表、MySQL 5.6/8 兼容性、版本 25→26 全路径及重复 `sync db`、append-only/哈希链断裂、伪造 JWT、重复请求、跨币/跨账户、授权过期、并发审计与撤销、重启后授权失效策略、交易网关 0 HTTP 调用与旧单退出职责不被静默关闭。

## 三、响应级成交来源核验（另一道独立 Gate）

在完成审计批准之前，`service/spotstrategy/s3_live_gate.go` 仍保留 `spotRealOrderReleaseApproved=false` 和 `canAttestLiveFills=false`，不允许修改以解锁真实下单。响应来源的实现应单独 Review：

1. 仅使用现有 SDK 签名主账户请求，校验 HTTPS、TLS 信任链、目标主网域名与可用代理传输配置（不能拿静态 BaseURL 字符串当作来源证明）。
2. 对每次查询关联当前授权主体、账户、币种、原始 ClientOrderID、交易所 orderId、tradeId、side、qty、quote、手续费币种、请求时间和响应收取时间；验证订单累积成交与逐笔 Fill 可精确对齐。SDK/代理/重试/429 的未知结果必须冻结，不得编造 Fill。
3. 持久保存最低必要的来源审计元数据；不能泄漏签名 URL、秘钥或用户私密原始请求。不能通过人为 UPDATE `rest_verified=1` 或 Fake 构造完成验收。
4. 在独立隔离环境完成正反例、部分成交/重试、人工挂单冲突、1m K线重复触发、手续费/第三资产换算与完整 BUY→Holding→SELL→PnL；才讨论实际资金小额受控验证。
