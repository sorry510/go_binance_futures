# 回测自定义精度差异与性能修复方案

> 日期：2026-11-20。状态：待开发 / 待 Code Review。基于本地 `go_bn_test` 只读核查及当前代码分析，非修改后的性能结论。

## 一、范围与原则

只解决两件事：**解释并校验 1m / 自定义精度的交易差异**，以及**显著减少自定义精度重复读取、解压和下载的开销**。

- 保留 Go + MySQL + Expr、`standard_1m` 与 `adaptive` 两套模式；不引入 DuckDB，不重构回测架构。
- 仅改本地代码和测试；**不修改生产数据库、不改 `conf/app.conf`、不清理历史回测数据、不修改实盘交易逻辑**。
- 费用、滑点、杠杆、开平仓规则、资金费、数据完整性校验和 Trades 先后顺序保持不变。
- 性能改动必须保持 `adaptive` 优化前后 **Trades / Events / Equity / Metrics / DataHash 及精度证据一致**；不能用跳过必要的精度判定换速度。
- `standard_1m` 与 `adaptive` 本就采用不同平仓价格/时间分辨率；不能以“最终收益完全相同”作为两模式验收要求。

### 1m 与 Adaptive 差异

按 `sequence` 对比 61 笔已平仓交易：

- 开仓方向一致：61/61；平仓原因一致：61/61。
- 开仓时刻和开仓价格一致：60/61；第 19 笔开仓差 1 分钟，需要单独查验前后持仓状态及信号时点。
- 平仓时刻、平仓价格各只有 1/61 完全一致；这是两模式收益差异的主要来源，需按真实时间顺序核实而非强行统一。
- 示例：第 1 笔 LONG 止损，1m 平仓价格 91,549.1025，Adaptive 91,639.5573；第 6 笔 SHORT 止盈，1m 68,642.0038，Adaptive 68,755.8607。
- 目前**未证明**存在计算错误，也**不能断言**所有差异都正确；尤其第 19 笔和分钟内双阈值、资金费边界应补对照测试。

## 三、代码定位

1. `service/backtest/adaptive_engine.go`：`evaluateROIClose` 先调用 `SecondBars`，之后大量秒区间调用 `evaluateTradeROIClose` → `Trades`。
2. `service/historicalmarket/resolution_provider.go`：`SecondBars` 在日级 1s ZIP 不可用/不完整时，调用 `Trades` 聚合出秒线；之后同分钟的逐秒 Trades 请求再次触发数据读取。默认 Provider 的 `writeSparse=false`，新数据不再写入 MySQL。
3. `service/historicalmarket/sparse_repository.go`：`LoadSparseTrades` 每次先查询 MySQL；本次回测 `trade_cache_hits=0`。
4. `service/historicalmarket/public_data.go`：`readPublicDataCSVRange` 使用单个前向 ZIP/CSV 扫描器；当新请求时间 `start <= scanner.lastTime` 时会重新打开 ZIP、从头解压。这在“先读整分钟 Trades 生成 1s，再逐秒请求 Trades”的回退路径下存在严重重复扫描风险。
5. `service/historicalmarket/resolution_provider.go`：默认持久 ZIP 缓存容量为 `2 << 30`（2 GiB）；检查时 `cache/tmp/adaptive-um-archives` 约 1.9 GiB，保有 63 个 BTCUSDT Trades 日级 ZIP，没有 1s ZIP。容量不足和清理机制可能解释第二次仍下载 5 份，但具体各归档被删除原因需要计数验证。
6. `service/backtest/store.go` 和前端回测页：`downloading_intrabar_archive`、`parsing_intrabar_archive`、`resolving_intrabar_data` 使用阶段提示；当前缺少将“正在读取缓存”“实际网络下载”“重复扫描”直观区分的进度统计。

**判断：P0 必须先消除同一候选分钟内重复的 Trades 加载，不能仅通过扩大磁盘缓存解决。** 数据库统计能证明高频调用量，但 ZIP 重开次数、解压 CPU 占比仍需补埋点或 pprof 量化。

## 四、修复步骤

### P0：分钟级 Trades 内存复用（优先开发）

**目标：相同候选分钟只加载/解析必要的 Trades 一次，后续逐秒评估在已验证的分钟数据中按时间与 TradeID 取切片，避免重复 MySQL 查询和 ZIP 解压。**

1. 让 `SecondBars` 从 Trades 回退生成秒线时，可将**同一分钟**的已读取 Trades 和对应来源证据传递或供调用方复用；不能引入全区间逐笔常驻内存。
2. 在 `evaluateTradeROIClose` 优先复用当前分钟的数据；只有未取得、覆盖范围不完整或证据不一致时才调用现有 `provider.Trades` 路径。按秒 `[start,end]` 边界和 `(TradeTime,TradeID)` 顺序过滤，保持同秒多笔成交先后不变。
3. 对已有真正的 1s 归档路径仍按原需查询 Trades；缓存生命周期严格限定单个候选分钟/单次回测，不跨策略、币种和并发任务共享。
4. 沿用原有 Trades/1s 来源、SHA256、覆盖范围、`ResolutionEvidence`、`DataHash` 计算口径；若一次数据复用造成 Evidence 记录次数/内容变化，必须先处理兼容，**不能只对比最终收益后就放行**。
5. 保持取消机制、内存有界、缺失/损坏数据报错；不跳过同秒双阈值歧义核实及原有资金费处理。

**验收：** 与基线完整对比 61 笔 Trades、Events、Equity、Metrics、DataHash 和精度证据；重复解析/扫描及 SQL 次数显著下降，冷热两次均成功且结果一致。记录峰值内存；不预定提速倍数。

### P1：归档缓存与读写路径小幅优化（P0 后开发）

1. 为 ZIP 打开次数、CSV 重置次数、解压行数、磁盘命中及真实下载数增加可读计数，先量化 P0 后剩余瓶颈。
2. 保留已验证 ZIP、SHA256、容量淘汰和旧稀疏缓存只读机制；优先消除同一文件的无意义重复扫描及重复校验，不缓存全部一年 Trades。
3. 评估当前 2 GiB 是否足以支撑 BTC 这种高成交量样本的热缓存复用；**不要直接无上限扩容**。必要时小幅上调或将容量作为已有缓存配置的可调整参数，但先给出新增磁盘空间和实际节省下载流量。
4. 确认 `1s` ZIP 缺失属于正常数据源覆盖限制还是可修复的来源问题；未证实前不假设 Binance 提供完整 1s 历史文件，更不能用伪造秒线代替。
5. 不做全量预下载，不恢复持续写入海量 `market_trades` / `market_klines_1s`。

**验收：** 相同冷/热样本下记录真实下载字节、ZIP 数量、缓存占用、重扫次数；缓存文件损坏时仍可重新校验/下载；不破坏 LRU 和并发引用保护。

### P2：回测页面阶段显示及性能统计

1. 后端区分实际 **网络下载 / ZIP 缓存命中 / CSV 解压解析 / 高精度回放计算**，而非统称“下载数据”；状态更新不影响回测执行及价格判定。
2. 前端显示当前阶段和有依据的计数（例如实际下载归档数、缓存命中数、已下钻分钟/秒数），避免热缓存时让用户误认为每次都重新下载。
3. 在 `resolution_stats_json.timing` 或现有统计结构中补上关键耗时与读盘次数，沿用现有记录与页面字段，不增加专门的监控子系统。

**验收：** 热缓存命中不显示为“正在下载”；实际下载时才展示下载；阶段更新不频繁刷库、不引入明显额外开销。

## 五、执行与 Code Review

按 **P0 → 验收 → P1 → 验收 → P2 → 总复审** 逐阶段执行；不一次性改完，避免性能提升后无法定位数据语义改变来源。

| 检查 | 放行标准 |
|---|---|
| 数据一致性 | 同一 Adaptive 样本修改前后逐笔交易、事件、权益、汇总、DataHash/精度证据一致 |
| 双模式差异 | 解释两种执行粒度的平仓差异；检查第 19 笔开仓偏移，不以两模式收益相同为目标 |
| 性能 | 固定相同历史窗口、策略、硬件和数据来源，对比冷缓存、热缓存及 P0/P1 各阶段的端到端耗时 |
| IO | 统计 SQL 次数、ZIP 重开/重扫次数、CSV 解析行数、下载次数/字节、内存峰值及缓存容量 |
| 可靠性 | 覆盖 1s 文件缺失回退、同秒 TP/SL、资金费边界、时间回退、缓存损坏/淘汰、取消/并发 |
| 测试与审查 | `go test ./service/backtest ./service/historicalmarket -count=1`、针对性重复测试、`go vet`，形成各阶段 Code Review 文档 |

**固定性能基线：** `standard_1m=10.54s`；Adaptive 冷缓存约 `60.56min`、已有缓存约 `33.15min`。这两个 Adaptive 样本的下载量不同，严格性能比较需要重复相同冷热条件；优化目标是先解决高频重复解析，再根据新的实测决定是否继续优化。

## 六、明确不做

- 不用 DuckDB，不更换历史行情数据库，不新建全量逐笔成交长期存储。
- 不改实盘策略/订单；不改止盈止损、手续费、滑点或 1m / Adaptive 的成交语义。
- 不以删旧库数据、禁用必要验证或扩大缓存占用冒充优化。
- 本文只记录修复方案与已观察证据，**不代表 P0～P2 已开发或已经获得性能收益**。
