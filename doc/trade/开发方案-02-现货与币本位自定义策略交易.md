# 方案 02：现货与币本位交易（个人版）

状态：设计稿，尚未实现。
优先级：P1，先做现货，完成后再做币本位。
前置：方案 01 的成交状态与部分成交修复通过验收。
范围：**只支持自定义策略**。不新建内置选币/内置交易策略，不复制全部 USDⓈ-M 交易代码。

## 1. 当前可复用内容

| 已有代码 | 用途 | 是否可直接复用 |
| --- | --- | --- |
| `feature/strategy/line/line_custom.go` | 自定义 expr 指标/策略规则 | 是，按市场提供变量 |
| `feature/account_trade_cycle.go`、`feature/feature.go` | 开仓/平仓判断、风控顺序、通知 | 复用决策思路和公共函数，不能直接照搬 Futures 类型 |
| `spot/api/binance/index.go`、`spot/spot.go` | 现货买卖 API、行情与旧自动买入功能 | 复用 API，不启用旧内置策略 |
| `models.SpotSymbols` 与 `spot_symbols` | 现货本地币种、策略配置及价格 | 是 |
| `feature/api/binance/delivery.go`、`models.DeliverySymbols` | 币本位行情、精度、币种 | 是，尚缺完整交易链路 |
| `service/futuresownership` | 请求幂等、累计成交差值、持仓归属 | 提取少量可复用逻辑；不可把 Spot/COIN-M 强行当 USDM 仓位 |

目标是**一套策略判断 + 每个市场一个薄交易适配器**。不设计统一 TradeOrchestrator 平台，也不为每个市场复制整套大型交易循环。

## 2. 简单实现方式

保留现有 `StartTrade` 的 USDM 入口，在业务层提取一个小型可复用执行函数：
- 输入：当前币种配置、现有策略、价格、已归属仓位/库存、交易预算；
- 输出：`BUY/SELL/OPEN/CLOSE` 的信号，是否通过风控；
- 由现货或币本位自己的 `placeOrder/queryOrder/queryFills` 小适配器完成交易；
- 订单状态、通知和部分成交遵循方案 01，不能在 HTTP 下单成功时写“已全部成交”。

最小接口只需：获取当前持有/余额、下单、查订单、查成交、撤单。利用现有行情 WS、本地币种表、定时任务；不强制新建一套完整 WebSocket 基础设施。

账户模型按市场隔离：`market=spot/usdm/coinm`、`account_id`、`symbol`、`owner`。共用的 `trade_fills` 有市场键；Spot/COIN-M 如确实需要保存独立策略仓位，只加各自的**最小归属数量记录**，不统一重建全部模型。

## 3. 现货开发（先做）

### 3.1 只支持这几项

- 使用现货 `spot_symbols` 的**自定义** `long`（买）与 `close_long`（卖）规则。
- 仅普通现货，不做杠杆借币、SHORT、保证金、自动换币、Alpha。
- 市价/限价买卖优先复用 `spot/api/binance/index.go`；与当前 Spot 抢新自动下单逻辑保持独立配置，互不认领库存。
- 下单前校验余额、最小成交额、最小数量、精度与挂单占用；卖出时只卖**该策略实际买入并归属的数量**，不得卖掉手动持有的余额。
- 不将 Fee 自动固定为 USDT：BNB/base/quote 扣费分别记录；现货净收益以实际 quote 币种显示。
- 无 Short 能力的策略配置直接给提示，不做自动改写。

### 3.2 最小数据

已有 `spot_symbols` 保存策略配置；成交记录复用方案 01 的 `futures_trade_fills`。
如果不能从现有数据安全得出“哪个币属于策略”，只新增 `spot_strategy_holdings` 一张极简表：
`account_id, symbol, owner, qty, avg_cost, status, update_time`，必要时记录 quote_asset；
同币同账户不同 owner 严格分离。取现货 `free` 余额与策略 `qty` 的较小值作为可卖上限，并考虑未完成卖单占用。

### 3.3 四步实施

S1. 在现货币种配置中增加自定义策略启用/预算开关（默认 OFF）；订单接口仍处于 mock，完成策略表达式与余额校验测试。
S2. 将现有现货 Buy/Sell API 接入订单查询、已成交记录、取消/超时补查；部分成交只增加真实库存。
S3. 实现“持仓归属 + 卖出残量 + 少量风控”，接现有监听/通知；断线可按订单 ID 补成交，不单独建复杂事件平台。
S4. 前端增一个“现货策略交易”页面或 tab，显示：策略、预算、当前归属币量、挂单、成交、盈亏；README/中英文；模拟验证后再手动开启真实交易。

**例子：**计划买 10，实买 4 后撤销余 6，归属库存只增 4（按真实手续费扣减）。随后卖出 1，归属剩 3，而不是清空该币全部账户余额。

## 4. 币本位开发（现货稳定后）

### 4.1 与 USDM 不同的必要规则

- 只做 **COIN-M 永续**（如 `BTCUSD_PERP`），不做季度交割。
- 下单单位是**张数**；名义价值依赖 contractSize，不能复用 `USDT / price × leverage` 公式。
- 币本位是反向合约，盈亏、手续费和保证金以币种结算；持仓数量、名义 USD、保证金币必须分开表示，不能当 USDT。
- 例如反向多单美元名义 N、入场 E、出场 P，毛收益以币计约为 `N × (1/E - 1/P)`；实际盈亏与手续费以 Binance 成交/账户记录为准。
- 复用 `delivery_symbols` 和已有 DAPI 市场信息代码，核实 contractSize、交易规则、持仓模式以及账户可用保证金币；缺失时不开新仓。
- 只运行用户配置的自定义 LONG/SHORT/CLOSE_*，不做新增内置币本位策略。
- 初期保持账户当前持仓模式；不自动切换 Hedge Mode，多空双开另由方案 04 控制。

### 4.2 四步实施

C1. 补齐币本位下单/查单/撤单/查询成交的 DAPI 薄封装；同步持仓/账户余额与合约乘数。
C2. 按合约**张数**实现数量精度、可用保证金和风险检查；币本位 ROI/PnL 单测重点验证 USD→币的反向计算。
C3. 复用方案 01 的部分成交处理和订单明细；币本位若不能直接使用当前 Ownership 数据结构，先补最小 coinm managed 数量表，而不是复制全套合约交易框架。
C4. 币本位独立配置与订单/仓位页面，支持用户手工启用；与现货及 U 本位开关、预算、手续费币种独立。

## 5. 精简后的文件改动范围

- 保留原 `feature/feature.go` 和 `account_trade_cycle.go` 的 U 本位入口；只把纯策略判断/订单状态公共函数抽出来；
- 现货：`spot/spot.go`、`spot/api/binance/index.go`、`models/spot_symbols.go` + 最小新交易入口；
- 币本位：`feature/delivery.go`、`feature/api/binance/delivery.go`、`models/delivery_symbols.go`；
- 已有 WS、通知、REST 限流模块尽量共用，不新建内部消息队列或新调度系统；
- 前端按市场增加简洁 tab；不在首页新增一大组菜单。

## 6. 验收门槛

- 现货不卖非策略库存，不卖超过真实 free 余额；不支持 SHORT 策略；重复成交不能重复增加库存。
- 币本位张数、保证金币与 PnL 计算正确，数量单位不能混淆；不把币本位手续费当 USDT。
- REST 提交后未成交不能报成交成功；部分开、部分平、取消、断线后查单均可恢复。
- 每个市场独立开关默认 OFF；不影响现有 U 本位交易；先 mock/测试环境，真实下单需要用户明确授权。

**本方案不做：**大型跨市场 Broker 框架、全部产品统一资产会计引擎、跨市场仓位合并、自动借币、跨账户自动资金划转、复杂财务报表。

官方材料：[Spot API](https://developers.binance.com/en/docs/products/spot/rest-api)、[币本位合约规格](https://developers.binance.com/docs/derivatives/coin-margined-futures/market-data/rest-api/Exchange-Information)。
