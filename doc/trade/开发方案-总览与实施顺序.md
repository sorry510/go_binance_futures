## 一、总体原则

- **个人使用、精简优先**：做实际要用的功能；只复用策略表达式、行情、限流、日志、通知等可明确隔离的公共能力。不引入统一 Broker、跨市场账本平台、内部消息队列或复杂调度。
- **两大新市场连续建设**：02 普通现货 → 03 币本位永续。二者分别有独立的账户验证、订单/成交/持仓账本、上线 Gate；03 复用 02 已验证的少量纯逻辑/状态规则，不复制 Spot 资产会计，也不直接写 U 本位表。
- **U 本位现有功能不回退**：04 双向持仓、05 加仓仍为独立的合约增强事项；与 02/03 不混做。
- **成交准确与安全高于功能数量**：下单 ACK 不是成交；每笔真实 Fill 去重，部分成交、部分撤单、UNKNOWN、断线和重启都要能恢复；不擅自认领别的 Owner 或手动仓位。
- **默认不自动交易**：行情监听、策略启用、实盘下单授权必须分别处理；现货旧自动交易与新策略自动交易按账户互斥，不能仅靠前端开关。
- **严格环境边界**：本地先 mock，测试库 `go_bn_test` 使用 `./go_binance_futures sync db` 升级；不改 `app.conf`、不写生产库、不发真实委托、不自动 commit/push。

### 02 → 03：连续交付、有限复用

**02 的 S4 完成并有复现测试证据后，进入 03 的 C0；不需要把 02/03 合并为同一个数据库/订单引擎。**

03 复用或参考的内容限定为：纯自定义表达式求值方式、客户订单 ID 幂等规则、订单状态转换与重启补录、tradeId 去重、API 错误分类及 Mock 测试夹具。03 不复用 Spot 的 base/quote 库存模型、现货买卖接口、手续费结算公式、持仓表；币本位的合约张数和保证金币必须独立。**02 实盘尚未部署不阻止 03 本地 Mock 开发；03 实盘也必须完成自己的 Gate。**

### 03：币本位自定义策略（C0 → C1 → C2 → C3 → C4）

| 步骤 | 重点交付 | 通过标准 |
| --- | --- | --- |
| C0 只读审计 | DAPI、主账户、One-way 状态、`contractSize`、保证金币、行情接线 | 账户/合约信息不可靠则停单 |
| C1 API 与数据 | DAPI 下单/查单/撤单/成交/持仓，三张最小 `coinm_managed_positions/orders/trade_fills` 表 | 私有链路独立，Mock/账户边界测试通过 |
| C2 策略与预算 | 按张数计算、币本位保证金及交易过滤器、开平规则与风险门禁 | 不用 U 本位 USDT 数量公式，不混淆单位 |
| C3 成交/恢复 | 真实成交去重、部分开平、撤单后恢复、仓位周期/结算数据核对 | 张数、手续费与币本位已实现收益可信 |
| C4 页面/回归 | 现有币本位区域配置/持仓/订单明细、告警、多语言与 Mock | 不影响 USDM、Spot；实盘默认 OFF |

COIN-M 首版只做**永续、单向持仓 One-way**；不自动切 Hedge Mode、不做交割合约。04 的 U 本位双向持仓不是 03 的首版前置，但后续进行 04 时必须评估 USDM/COINM 账户模式联动及已经启用的 COINM 安全门禁。

### 04、05：独立 U 本位增强

- **04 双向持仓**：按 `symbol + positionSide` 区分多空两条腿、各自止盈止损和归属；不自动更改账户 Hedge Mode；依赖 01 的准确成交关系。
- **05 合约加仓**：同一持仓周期新增 `ADD` 成交、持仓成本和风险限额；推荐在 04 验收后实施，但不属于 02/03 的改造内容。

### 06：Alpha 交易，低优先级独立支线

先核实官方是否真正支持个人账户 API 下单、查单、真实成交、撤单和余额查询；不具备完整条件时停止自动交易开发，仅可按需做公开行情只读预览。**不得把 06 的 API 可行性作为 02/03 的前置。**

## 四、市场数据模型边界

## 五、验收及部署边界

- 本地阶段：方案文档、源代码、模拟交易、目标 Go 测试/构建与 Vue typecheck/build；新增市场一次只推进一项主交易功能。

- 生产上线：每个市场分别获得真实余额/订单/成交对账、可回滚 release 包、数据库版本与用户明确授权。未通过不得触发真实委托、撤单或账户设置切换。
- 本轮只更新 `doc/trade` 的规划、文件编号和必要交叉链接，不改 Go/Vue、数据库、账户、订单；不自动 commit/push。
