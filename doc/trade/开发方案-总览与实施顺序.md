## 一、总体原则

- 个人自用：只做实际要使用的功能，优先复用当前 Go 交易循环、Ownership、Binance SDK 和前端菜单。
- **只保留一份“方案 01”**；所有阶段直接写在该文件中，不另建第二份 01 补充方案。
- 新的市场只支持自定义策略；不引入大型通用交易框架、跨市场统一财务引擎或复杂分布式架构。
- 可不迁移旧交易历史，但不能清空/放弃当前仍在 Binance 实际持有的仓位。
- 下单 ACK ≠ 实际成交；部分成交、误归属、重复下单、止盈止损及资金风险是必须保留的安全边界。
- 每完成一个功能及其验收再进入下一个实盘功能；新增市场与加仓默认关闭。

## 三、正式执行顺序

### 第一阶段：01 合约订单与历史重构（现在开始）

执行文档：[方案 01](开发方案-01-合约订单审计与部分成交.md)，只按**这份文件**工作。

| 步骤 | 交付内容 | 完成后验证 |
| --- | --- | --- |
| **01-0** 现状确认 | 识别旧 order 引用、全部受管理 owner、活跃仓位与风险联动 | 明确现有持仓如何不中断管理 |
| **01-1** 数据模型 | `managed_orders.position_id`、条件单真实订单 ID、**一张** `futures_trade_fills` | 新开新平有稳定关联、DB 原子回滚 |
| **01-2** 成交正确性 | 逐笔 Fill、WS/REST 补查、去重、部分成交加权均价修正、Algo 实际订单号关联 | 部分成交及重复事件结果正确 |
| **01-3** 完整结算 | 多次平仓、余量、手续费/PnL；连续盈亏控制改为确认结算后一次 | 不提前平仓、不重复触发策略风控 |
| **01-4** 旧表退役 | 移除旧 `order` 读写、定时猜配/删除、旧页面 DELETE；**不迁移旧历史** | 全业务不再依赖旧表，活跃仓位安全 |
| **01-5** 前后端 | 主表每行一个 `position_id`；展开开/平订单和真实 Fill | 一开多平只一行、同币下一轮另起一行 |
| **01-6** 整体验收 | 后端测试、异常/重启恢复、Go/Vue 构建、多语言、旧真实持仓不失管 | 得到可交付版本，再考虑部署 |

**注意：**实现时可以把紧密相关的小步骤合并为一批代码提交，但不能省去验证环节。旧 `order` 表物理 DROP 不在第一阶段内；不迁移不代表立即删除数据库表。

## 四、跨阶段共用的数据约定

- `futures_managed_positions.id`：一次持仓周期，**主表一行**；关闭后再次开仓生成新 ID。
- `futures_managed_orders.position_id`：一笔开仓、平仓、止损或未来加仓属于哪个周期；旧表不猜测配对。
- `futures_trade_fills`：唯一新增的真实成交明细表；同一交易所成交不重复记账。
- `futures_orders`、`futures_positions`：仍是 WS/REST 实时状态镜像，非历史成交真相。
- 不迁移、不修复、不展示旧 `order` 历史；现有已持仓不可因为缺新历史而失去风控。
- 部分成交、条件单真实订单 ID、成交手续费、实际已实现盈亏和不完整状态应在方案 01 一次性做对，其他方案再复用。

## 五、每阶段最低验收要求

1. 交易所只收到一笔的订单不能在本地出现两笔成交；WS/REST 重复和重启后数量不重复。
2. 开仓委托 10、实际成交 4、平仓先 1 再 3：一条主行和三条子订单，开 4、平 4、剩余 0。
3. 某币种本轮平仓后重新开仓，必须生成新持仓 ID，不能并到旧主行。
4. Algo 条件单触发成交不会因为 `algoId` 与真实 `orderId` 不同而丢 Fill。
5. 用户手动减仓、未知持仓、旧仓位缺历史时显示“明细不完整/待核对”，不伪造收益，不擅自归属。
6. Binance 下单失败、DB 持久化失败、网络 UNKNOWN、保护单异常时不会显示虚假的成交成功。
7. 新功能始终默认关闭；每次部署及生产数据库升级由用户另行授权。
