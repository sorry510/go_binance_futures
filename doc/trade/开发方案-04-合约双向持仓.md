# 方案 04：合约多空双开（个人版）

状态：设计稿；先完成方案 01 的成交可靠性修复。
目标：在同一个 USDM 交易对上允许 LONG 和 SHORT 同时存在，独立开仓、平仓、止盈止损；不新建复杂多账户交易系统。
规模：主要改现有方向判断与风险判断，**不需要重做 Ownership**。

## 1. 当前为什么不能双开

从源码确认：
- `models.FuturesPosition`、`models.FuturesOrder` 和 Managed 表**已有 positionSide**。
- `feature/trade_cycle_snapshot.go` 已能按 `symbol|positionSide` 判断持仓或挂单。
- `service/futuresownership` 也按币种 + 方向 + Owner 管理实际持仓，可复用。
- **真正明显的阻挡点在 `feature/feature.go`**：`openBlockedSymbols[position.Symbol]=true` 和后续按整个 symbol 跳过新开仓，有 LONG 就不允许开 SHORT。
- 主账户 `EnsureConfig` 当前可能忽略 Binance 配置更新错误，双向模式开启前需要补明确的模式检查。
- 旧 `order.closeOrderId` 一对一记录不适合两条腿共存，必须依赖方案 01 的成交事实。

因此，这不是“从零实现 Hedge Mode”；是在**已有按方向数据模型**上补足交易入口与保护逻辑。

## 2. 范围及安全限制

- 一期只支持 USDM 主账户，在用户主动开启后允许 LONG/SHORT 同币共存；同一方向仍不允许重复开仓（加仓由方案 05 处理）。
- Binance Hedge Mode 由用户自己确认/切换，系统只使用已有 `GetPositionModeContext` **读取并校验**，绝不自动切换账户模式。
- 实施时确认 USDM/COINM 的账户模式联动及已有持仓/挂单影响，不能假设只影响一个币种。
- Hedge Mode 下委托必须填明确的 `positionSide=LONG/SHORT`；不得沿用 One-way 的 BOTH 语义；`reduceOnly` 在 Hedge Mode 不接受，保护单参数必须按官方接口验证。
- 未归属的 LONG/SHORT 不能自动划给策略；另一条腿的订单、持仓和保护单不得被动修改。

## 3. 只需要处理五类逻辑

### 3.1 修改币种屏蔽的 key

将 `openBlockedSymbols` 的键从 `symbol` 改为 `symbol|side`；判断开多时只看 LONG、开空时只看 SHORT。同一方向已有持仓或待成交开仓单仍阻止第二笔 OPEN。

必须同时检查 `hasPositionLong/Short`、`hasBuyOrderLong/Short`、`Owner` 归属，防止放开屏蔽后误开和重复下单。

### 3.2 校验账户 Hedge 状态

在交易轮次开始时或受控短时缓存内读取当前账户模式：
- 开关关闭：沿用当前行为；
- 开关打开，交易所不是 Hedge：不下新开仓订单，输出一次明确日志；
- 交易所 Hedge 但本地数据方向未知：先从 REST/WS 对账，暂停新增风险；
- 不需要开发自动切换模式的服务或复杂权限体系。

### 3.3 按方向正确下单

| 交易动作 | side | positionSide |
| --- | --- | --- |
| 开多 | BUY | LONG |
| 平多 | SELL | LONG |
| 开空 | SELL | SHORT |
| 平空 | BUY | SHORT |

订单 ACK 仅表示已提交；实际是否有仓位由方案 01 的成交/交易所持仓确定。平仓数量不得超过该 Owner、该方向已确认的可平数量。

### 3.4 双向风控与保护订单

- 仓位数量按照 `(symbol,LONG)` 与 `(symbol,SHORT)` 分别计数。FutureMaxCount 可以沿用现有“每方向 1 个 slot”口径，前端写明含义。
- 每边独立 TP/SL、成本和未实现盈亏；另一边不能因为某方向平仓就被取消保护单。
- 双边资金使用量按总名义敞口和保证金控制，不能因为净敞口接近 0 就认为没有风险。
- 一条腿数据不确定，只暂停该腿的新开仓；已确认安全的退出和另一腿逻辑尽量不受影响。

### 3.5 简单前端

现有合约币种配置增加“双向策略开仓”总开关（默认 OFF）；只读显示交易所当前模式。
持仓、订单页面按照 LONG/SHORT 两行独立显示数量、收益、挂单和策略来源。不开新管理后台，不引入方向专属一整套配置中心。

## 4. 开发步骤（三步）

**H1：模型/判断修改**
- `feature/feature.go` 调整 blocked key 与入场顺序，保持退出逻辑原样；
- `feature/trade_cycle_snapshot.go`、`service/futuresownership` 检查现有方向键与唯一约束，修复遗漏；
- 用 mock 验证同币双向都能产生候选，但同向重复开仓仍被拒绝。

**H2：账户校验/订单安全**
- `feature/api/binance/account_client.go` 使用现有模式查询；模式不符禁止新开；
- 逐项核对普通单和 TP/SL 参数的 Hedge 兼容性；不自动发模式切换请求；
- WS/REST 对账、平仓订单和通知均必须显式保留 positionSide；若模式未知 fail closed。

**H3：页面与灰度**
- 配置开关、两腿独立持仓/订单展示、中英文/README；
- 先 mock/官方测试环境，人工确认后小额验证；现有默认 One-way 的策略行为必须保持一致。

## 5. 必须通过的测试

1. LONG 已持有，SHORT 仍可开仓；反过来也可以。
2. 两腿共存，平 LONG 不影响 SHORT 的真实数量、Owner 和保护单。
3. 同方向已经有 OPEN/PARTIALLY_FILLED 订单时不能重复开。
4. 账户非 Hedge 或模式读取失败时不能发 Hedge 新单；不尝试自动切模式。
5. 平仓只减对应方向的已成交量；部分平仓后保护单只针对余量。
6. 手工/未知 Owner 仓位不被认领；重复 WS 和断线后的持仓一致。
7. 双边占用总保证金，风控不能只看净敞口。

## 6. 明确不做

不做“自动把账户切成双向模式”、跨账号策略管理、多套方向调度服务、复杂对冲比率引擎、杠杆动态调整、自动平衡多空规模。

涉及文件：`feature/feature.go`、`feature/trade_cycle_snapshot.go`、`feature/account_trade_cycle.go`、`feature/ownership.go`、`service/futuresownership/*`、`feature/api/binance/account_client.go`、现有合约页面。
