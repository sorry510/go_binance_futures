# 方案 06：现货策略异常订单恢复操作边界（未放行）

日期：2026-11-12

本文件用于说明现阶段已有的**可观察能力**、缺失的**可执行恢复入口**，以及遇到异常时的安全处置原则。**不是可以直接操作生产账户或数据库的恢复指令。**

## 一、当前可用的最小诊断

- 登录后访问「现货量化交易 → 仓位与受控交易」，按币种/状态筛选本策略持仓与本地 Order；打开详情可看到该周期的 BUY、SELL 和不可变逐笔 Fill，以及 `review_issues`。
- 相关 API：`GET /spot-quant/orders`、`GET /spot-quant/positions`、`GET /spot-quant/positions/:id`。这些只读本地记录，**不会读取 Binance 权威订单或恢复未落库成交**。
- 页面上唯一可执行的修复操作 `POST /spot-quant/positions/:id/rebuild` 仅从**已存储的 Fill** 重算物化仓位字段，需要二次确认和通过本地订单一致性复核；**它不是交易所对账**，不能拿来释放未知 `NEW` 订单。
- 订单 REST 对账和未知 `NEW` 的 `ConfirmNeverAccepted` 目前只有 `spotexecution.Processor` Go 方法，没有生产 HTTP/CLI/UI 运行时接线。页面的卖出、撤单和交易所对账按钮保持禁用。

## 二、异常时的安全决策

| 情况 | 当前处理 | 不允许 |
| --- | --- | --- |
| 本地订单 `NEW`，交易所请求超时/状态未知 | 停止该币新单，保留原 `client_order_id`、原始异常日志、交易所订单/成交证据；等待安全的权威 REST 对账入口 | 重发原订单、创建不同 client ID 规避门禁、直接改库为 REJECTED |
| 交易所返回 `-2013` 未找到 | 不能单凭一次结果释放；代码要求 30 分钟后两次权威查无此单、原单未绑定且无 Fill，人工确认 | 把网络失败视为查无订单；自动关闭已有成交周期 |
| `FILLED` 比 myTrades 先到、部分成交、手续费资产不明 | 保留 `ErrNeedsReview`；由未来的 Testnet 只读恢复入口核对 `orderId/clientId/tradeId` 和手续费 | 以本地 order.status、可修改的物化 PnL 替代逐笔 Fill |
| SELL 基础币手续费导致低于 LOT_SIZE 的 dust | 保留 OPEN/异常，记录当前策略剩余量和真实余额；等待受控人工处置流程通过 Testnet | 假造 `CLOSED`、出售人工持币、删除真实 Fill |
| Testnet 账户 `-2015` | 修正 Spot Testnet 凭据、权限和 IP 白名单后只读复验 | 退回主网 Key、开启主网订单、篡改 `conf/app.conf` |

## 三、未来解除 F5 阻塞的最小条件

1. 具备正确、独立的 **Spot Testnet** API 凭据，签名账户及权威查单权限通过；明确不会访问主网交易地址。
2. 提供一个**仅显式人工调用**的恢复入口：按本地 `order_id` 或原 `client_order_id` 对账；将 `Reconcile` / `ConfirmNeverAccepted` 绑定到独立 Testnet 适配器，禁止未经确认的新 BUY/SELL。操作结果返回可复核订单/Fill 状态，不暴露 API Key。
3. 未找到订单的释放严格复用当前 `Processor.ConfirmNeverAccepted` 的 30 分钟、两次权威查询、空 Fill、原单 `NEW`、原 exchange ID 为空等所有前置条件；释放后迟到 Fill 仍报需复核，不静默重开旧周期。
4. 增加 HTTP/CLI 的未认证、错误环境、网络超时、重复调用、部分成交、错符号、重启后恢复的永久测试，再让用户决定是否开启受控人工入口。
5. **主网真实成交、自动信号接线与生产发布**必须另行通过 v25 物理 Schema、Testnet BUY/SELL/WS、MySQL 8 性能与回滚门禁，且须得到用户明确授权。

**现阶段结论：F5 的 Go 方法已就绪，实际操作入口尚未实现或放行；异常只能先诊断与停新单，不能建议直接改数据库。**
