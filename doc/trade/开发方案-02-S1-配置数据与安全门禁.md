# 方案 02 · S1：现货策略配置、最小数据与安全门禁

更新：2026-11-09
状态：**待开发**；不得把规划字段视为已在数据库创建。
上游：[S0 现状审计](开发方案-02-S0-现状审计与安全边界.md)；下游：[S2 私有 REST 与订单状态](开发方案-02-S2-私有REST与订单状态.md)。
目标：完成可测试的数据约束、单币策略配置及新旧自动下单入口统一守卫，但**本阶段不接入任何可用的真实策略下单通路**。

## 1. 范围与执行限制

- 仅 `account_id=main`、`owner=auto_strategy`、普通现货 `LONG/CLOSE_LONG`。任何其它 account、owner、SHORT/借币一律拒绝。
- 交易配置从 `spot_symbols` 读取；`listen_symbols` 继续原样提供自定义通知。复用纯 expr/K 线指标求值方式，不直接运行硬编码 `futures_positions` 的 `line_custom.go` 分支。
- 提供全局 `spot_auto_trade_mode=legacy|strategy|off`，**旧有行为默认保持 legacy**；每币 `strategy_trade_enabled=0`，另有明确的模拟/实盘权限边界，默认**不可真实下单**。
- 模式转换按 S0 的活动订单和历史风险清单判断；仍运行的旧功能有未完成退出责任时禁止切到 strategy，不悄悄取消订单、不接管币。
- 限定 S0 识别的**仍计划保留**的自动 Spot 写接口（特别是 `spot.TryRush`、`spot.NoticeAndAutoOrder` 所触及的调用点）必须使用同一个后端门禁。已明确计划废弃的 `eatRate` 不纳入功能开发与兼容测试；实盘启用前确认其调度已停用。若单一 `legacy|strategy|off` 模式无法安全表达**保留功能的**安全退出，**S1 先停下重新审议**，不可硬切断保护/退出。

## 2. 最小数据库结构（S1 需要落实为明确 DDL）

本期预计 **三张新表**，不写入现有 `futures_managed_positions`/`futures_managed_orders`/`futures_trade_fills`。字段按 S0 证据微调，修改后同步本文件并补测试。

### 2.1 `spot_strategy_holdings`：策略归属库存周期

| 字段 | 要求 |
| --- | --- |
| `id` | BIGINT 自增主键，周期唯一 |
| `account_id,owner,symbol,base_asset,quote_asset` | 非空；账户/Owner/交易对的强关联 |
| `owned_qty,avg_cost_quote` | DECIMAL 高精度；当前**净**归属 base 数量、按 base 计的 quote 成本；不得由委托数量填充 |
| `status,created_at,updated_at,closed_at` | `active/closed/reconcile_required`，完整卖出后关闭；同币再开新周期 |
| `active_slot`（建议） | 活跃持有时唯一的 `account|owner|symbol`；关闭设 NULL，避免同时建多个活跃周期 |

### 2.2 `spot_strategy_orders`：订单意图与恢复锚点

| 字段 | 要求 |
| --- | --- |
| `id,account_id,owner,symbol,holding_id` | 本地订单 ID、显式归属；尚未实际成交 BUY 的 holding_id 可为空 |
| `side,order_type,intent` | BUY/SELL、MARKET/LIMIT、open/close |
| `client_order_id,exchange_order_id,signal_key` | **提交前**写 client ID；exchange ID 在 ACK/查询后补；`signal_key` 按策略/闭合 K 线做持久防重 |
| `requested_qty,filled_qty,executed_quote_qty,reserved_qty` | 高精度数量、累计已成交、实际 quote 值与持有资源占用 |
| `status,created_at,updated_at,last_checked_at` | `reserved/submitting/unknown/new/partially_filled/filled/canceled/expired/rejected/reconcile_required` |
| `last_error`（可选） | 有界错误信息，不能写 API Secret、Cookie、完整隐私载荷 |

### 2.3 `spot_strategy_fills`：唯一真实逐笔成交

| 字段 | 要求 |
| --- | --- |
| `account_id,symbol,order_id,trade_id` | 四元组唯一；同一 REST 成交重复导入零增量 |
| `holding_id,client_order_id,side` | 所属库存周期及订单；必须精确匹配，本地无关联则保留待核对，不能按时间猜 |
| `qty,price,quote_qty,commission,commission_asset,trade_time` | 高精度原始十进制；手续费资产明确，精度不足则拒绝误记 |
| `rest_verified` | 真实 REST 可信标志，不能将 mock 标记成实盘核实 |

**索引/约束**：`orders.client_order_id` 在本账户业务范围唯一、`(account_id,owner,symbol,signal_key)` 防同信号重复；`orders(holding_id,status)`；`fills(account_id,symbol,order_id,trade_id)` 唯一；`holdings(account_id,owner,symbol,status)`。只有能与 MySQL 5.6/8 和测试 SQLite 兼容的约束才纳入最终 DDL，严禁仅靠代码判断“肯定唯一”。

**并发边界**：首次 BUY 尚无 holding 行可锁，必须对已有币种配置行或等价稳定的单账户/币种锁定对象加事务锁，再查询 pending 单并创建预留；避免两个 goroutine/实例同时发两个首单。活动周期用唯一 active slot 兜底，状态写入和预留失败时必须回滚。不要为此另建大型事件/资源分配平台。

## 3. 数据库迁移和模型

1. 以实际 `appversion.DatabaseSchemaVersion` 为准；当前 v24，若无其他版本变更则 S1 增至 **v25**，若已升级则顺延，不能硬编码忽略新版本。
2. 更新 `models/spot_symbols.go`（建议显式 `strategy_trade_enabled`、`strategy_budget_quote`）；不要复用含糊的 `enable` 或假定 `usdt` 永远是 USDT。预算同时记录/校验 quote_asset。
3. 全局模式加入已有合适的配置模型；必须确认是**持久配置**，重启后不会因默认值而偷偷开启新策略。
4. 增加三个独立 Beego ORM 模型；按实际使用方式登记模型。涉及 DECIMAL 时使用可靠的显式 SQL DDL/迁移，不允许 ORM 将金额建成浮点/字符串而静默改变精度。
5. 遵循 `command/db_update.go`、显式 Go migration 与 `command/db_update_test.go` 的版本路径；新建和从 v24 增量升级都应正确。所有正式升级只能执行 `./go_binance_futures sync db`；先 `go_bn_test`，不修改 `app.conf`，绝不自行升级生产库。
6. 配置 API 后端校验：币种存在、交易对合法、预算正数、账户权限正确、策略规则只允许合法方向；旧字段不丢失，批量修改不得绕过新交易开关。

## 4. 门禁的可测试契约

所有 Spot 下单入口接收**明确调用来源**，在真正调用 Binance Create/Cancel 前后端执行统一 Gate：
- `legacy`：旧风险增加按 S0 既有规则，策略订单拒绝；`strategy`：新策略只有在 per-symbol enabled 且实盘独立授权才允许委托，旧新冲突须拒绝；
- `off`：拒绝任何自动新开风险；保留受控只读/恢复路径，**安全退出职责依据 S0 做专门判断，不能简单全停**；
- 未知账户、缺余额/挂单、配置不一致或外部订单无法归属：拒绝新风险，记录审计原因；
- UI 只能配置状态，不能绕过服务端门禁。原 Spot 监听/WS 继续可用。

S1 的 `placeOrder` 始终被 mock/stub 或硬拒绝：**S1 Gate 通过也不代表能向 Binance 发真实订单**。

## 6. 自动化测试与 Gate

- [ ] 默认新策略全部 OFF；升级旧库、第一次安装、服务重启均保持旧模式/现有监听结果。
- [ ] 主账户与 Owner 以外直接拒绝；不凭空产生实盘订单，不能借用 USDM/COINM 的对象。
- [ ] 仍保留的旧 Spot 自动写入口都有守卫，不要求重构已经计划废弃的 `eatRate`；**不得误终止必要平仓/退出**。
- [ ] 活跃委托/策略归属未知时，切换到 strategy 返回明确拒绝原因，不执行自动撤单或划转。
- [ ] 两个并行首次 BUY 只能成功预留一次；重复 `signal_key/client_order_id` 不产生两笔记录。
- [ ] 3 张表结构、DECIMAL、索引、唯一约束及事务回滚通过数据库测试；新库和升级库都可复现。
- [ ] 模拟表达式可用且 `short` 通知不等于平仓；现货监听不回归。
- [ ] 针对已修改包执行 Go 单测/构建、`git diff --check`；标记独立已知失败，不宣称全仓绿。

**S1 → S2 条件：** 账户模式和真实下单守卫全覆盖、DB 结构可靠、策略配置正确、迁移在测试库通过，且还没有任何新策略实盘委托。
