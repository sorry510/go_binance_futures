## 三、MySQL 8.0.46 隔离 Schema 与合成负载验证

测试环境：**本机 Docker ARM64 临时容器**，MySQL **8.0.46**。下载官方 `mysql:8.0` 测试镜像；在 `/tmp` 中使用 `conf/app.conf.example` 创建独立**测试专用**连接配置，**没有修改实际 `conf/app.conf`**。用当前后端源码编译的临时二进制，在全新 `spot0674_test` 临时库中执行唯一允许的升级入口：

`./go_binance_futures sync db` → **EXIT 0**。

- `config.version=25`；Spot Managed 业务表全部生成。
- Spot 4 + Order 2 + Fill 4 = **10 个财务字段均为 `DECIMAL(36,18)`**。
- 订单 client/exchange 唯一索引、仓位 symbol/status 索引、订单 position 索引、Fill position/order/交易去重索引均存在。
- **只在此临时库**填入 500 个合成 CLOSED 周期、1000 张订单、1000 条成交 Fill，运行 MySQL 8 `EXPLAIN ANALYZE`。未写任何现有开发数据库或生产库。
- 一次执行计划样本（仅数据库服务器内部执行时间，**不是 P95**）：
  - BUY 历史查询：`PRIMARY` 反向索引扫描 1000 行，约 **0.34 ms**；
  - 未结订单条件：`PRIMARY` 扫描 1000 行，约 **0.47 ms**；
  - symbol 持仓分页：`PRIMARY` 反向扫描 200 行取 100 行，约 **0.08 ms**；
  - position_id Fill：`idx_spot_fills_position` 查 2 行，约 **0.02 ms**。
- 这证明 **MySQL 8 的迁移和有限规模的实际 SQL 执行兼容**，同时揭示订单历史/未结查询尚有整索引扫描，**不能当作生产历史量级、网络延迟或 2 秒轮询 P95 的验收**。上线前仍需生产真实体量下只读 `EXPLAIN` 与代表性压力测试。
- **临时 MySQL 8 容器已自动删除并经 `docker ps -a` 核验为 NONE**；保留的只有本地 Docker 下载镜像与可清理的 `/tmp` 测试文件。
- **没有执行**真实开发库或生产库的 `sync db`、DDL/DML；生产 v25 同号历史旧表的物理 Schema **尚未核验**，发布前 7 项检查单仍不能勾选。

2. ticker 过期 8 分钟：**不 BUY**。

4. 5m Kline 已过期 30 分钟：**不 BUY**。
5. 行情修复后，真正的 `spotexecution.Processor` 完成 BUY/Fill；然后人为令 ticker 过期，即使浮盈触发 `close_long` 也**不 SELL**。

以上仅使用**隔离 Fake Kline/Spot Exchange + 临时 SQLite**，不是 Binance 真实行情推送、账户成交或成本证据。

5. **生产发布与回滚**：尚无固定的已提交前后端 Git SHA 对应 Linux/ARM 构建物和备份证据；未部署、未重启服务、未修改主网适配器；异常订单人工恢复入口的原 06-ALL 问题也未自行关闭。
