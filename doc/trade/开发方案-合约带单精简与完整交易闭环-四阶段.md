# 开发方案：合约带单精简与完整交易闭环（四阶段）

> 状态：**Lead-01 本地开发与回归完成（不兼容旧配置），详见 CODE_REVIEW_Lead-01.md；Lead-02～04 尚未开始**  
> 适用项目：`go_binance_futures`（Go 后端）、`go_binance_futrues_new_ui`（Vue 前端）  
> 目标：单用户个人系统；**复用现有合约交易逻辑，只保留 Lead 账户必需的隔离和资金安全机制**。  
> 原则：不新增审批流、运营治理平台、第二套交易引擎、策略编辑器、重复的业务配置或无必要的数据库表。每阶段完成开发、单测、Code Review 后再进入下一阶段。

## 一、背景与现状（以 2026-11-17 本地源码为准）

这次现货量化交易暴露了两个值得避免的问题：

1. **停止开仓 ≠ 禁止管理已有仓位**：开关的作用必须贯穿策略扫描、下单前校验与真实执行器，不能因关闭开关阻断已管理仓位的正常退出和订单对账。
2. **短周期调度 ≠ 每轮重新请求全部 REST**：同一周期要复用已有行情/账户快照、优先处理仓位与未结订单，并保留 Binance 统一 Weight 预算。

当前 Lead 已有大量基础代码，但**没有完成生产自动交易链路**：

| 模块 | 源码事实 | 当前结论 |
| --- | --- | --- |
| Lead 独立账户 | `feature/api/binance/account_client.go` 有独立 Lead API Client；`credentials.go` 有 AES-GCM 凭证文件 | 保留，不能退回 Main 凭证 |
| 策略/选币 | `feature/account_trade_cycle.go` 已抽象账户型 Runner，Main 入口复用 `smart_local_v2`；Lead 生产 Runner 仍被测试专用 Permit 限制 | 需要接通 |
| 交易执行 | `service/leadaccount/executor.go` 有 `ExecuteOpen` / `ExecuteManagedClose`；`execution.go` 的只读 Broker 拒绝 Submit/Cancel | 尚无可运行的生产开平仓 |
| 运行入口 | `main.go` 只可按 `BINANCE_LEAD_OBSERVER_MODE=read_only` 启动只读观察器；`controllers/lead_account.go` 的 `/start`、`/reconcile` 返回 423 | 未形成自动调度及可写对账 |
| 风控/治理 | `service/leadaccount/management.go` 对 `enabled/allow_new_opens` 永久拒绝启用，`LeadDurableOpenGate` 始终拒绝；另有 RiskController、Audit、Supervisor、Mirror、告警队列 | 存在复杂度和重叠，应精简 |
| API 限额 | `lead_order_limiter.go` 本地订单配额 16/18 次每 10 秒；`binanceapiusage` 统一 IP/订单预算；SAPI 币种缓存约 1 小时刷新 | 有基础，但未完成双账户真实负载证明 |

**关键前提：当前 Lead 实盘被锁定是明确的安全边界，不允许通过删除一行校验、伪造 Portfolio 认证或使用 Main 凭证来“解锁”。** 本方案的第 1、2 阶段保持无真实下单；第 3 阶段先完成隔离/模拟链路，第 4 阶段按独立的真实交易验收逐步放行。

### 设计边界

- Lead 是**独立的 Binance Lead 账户/Portfolio**，不是复制 Main 实际订单，更不是同步跟单用户的订单；复用的是 Main 的选币、策略计算与交易流程。
- Main 和 Lead 的余额、仓位、挂单、API Key、User Data WS、交易订单、Ownership 必须严格分离。
- 对同一账户的 Managed 持仓只能按有真实 Fill/Order 证据的数量平仓，**不能自动归属手动持仓**。
- 不变更 `conf/app.conf` 里的数据库连接；不写生产库；需要 Schema 修改时按既有 `./go_binance_futures sync db` 升级流程，避免运行时自动迁移。
- 保留当前 Lead 实盘锁定，直到阶段 4 的真实环境 Gate 全部满足并由用户明确启用。

## 二、阶段 1：架构收缩与配置精简（Lead-01）

### 目标

清理“为多人审批/独立治理平台准备”的重复层和配置，让 Lead 与主合约的差异仅限于账户身份、资金和必要的风险限制。**这个阶段不接通真实下单。**

### 保留

1. 独立 Lead API 凭证及不可回显的 Secret；隔离 Main/Lead 的 SDK Client、WS、数据库 Ownership 和订单查询。
2. 真实订单幂等 `clientOrderId`、逐笔 Fill、持仓归属、交易所参数校验、异常订单的只读恢复能力。
3. 统一的 Binance API Weight/订单预算与 429/418 退避。
4. 必需的运行日志与错误原因码；已有的账户认证和最小权限控制。

## 三、阶段 2：复用合约选币与策略，接通 Lead 调度（Lead-02）

### 目标

不重写主合约选币或指标引擎，在**独立 Lead 账户上下文**中构建完整的只读/模拟执行周期：选币 → 计算信号 → 判断已有仓位 → 形成开平仓意图。阶段结束仍不提交真实订单。

### 实现顺序

1. **复用选币**：基于 `feature/account_trade_cycle.go` 的 `accountTradeRunner` / `selectConfiguredCoins`，不再复制独立选币实现。候选集合先经过 Lead 可交易币种白名单过滤，再按现有选择规则计算。白名单缺失/过期时禁止新开仓。
2. **复用信号**：使用既有 LONG/SHORT 和 CLOSE_* 策略、K 线与指标；不增加 Lead 策略模板/指标编辑器；两账户结果可以独立执行但不能读取对方仓位。
3. **先持仓，后开仓**：每轮**先检查 Lead Managed 持仓、保护单和未结算订单**，再处理允许新开仓的币。不开启新仓时仍允许已有仓位触发 CLOSE_LONG/CLOSE_SHORT、保护单维护及对账。
4. **单轮快照共享**：一次调度复用同一时刻可验证的新鲜账户、仓位、订单快照；不要“每币重拉账户/收益历史”。真正提交交易前仍重新校验关键余额、仓位、交易所规则及订单状态。
5. **调度去重**：维持与现有主合约一致的调度入口，禁止同一 Lead 周期重入、同一币种重复信号/重复 `clientOrderId`、异常反复快速请求。
6. **独立故障状态**：Main 的 429、WS 断线、订单错误不能将 Lead 余额/仓位替换为 Main 值；Lead 错误也不能触发 Main 非预期下单。

### 代码范围（以最终 Code Review 为准）

- `feature/account_trade_cycle.go`、`feature/feature.go`：复用策略流程，但不能直接去掉目前生产 Lead 的 Mock Permit 并让它触发实盘。
- `feature/api/binance/account_client.go`、`lead_symbol_cache.go`：绑定 Lead SDK、白名单，避免每币都查 SAPI。
- `service/leadaccount/`：绑定唯一的 Lead runtime、信号和只读/模拟执行适配层。
- 前端 `src/views/futures/leadTrading.vue`：展示调度状态、有效币数、阻断原因及模拟决策；不新增审批入口。

### 必须测试的场景

- [ ] 6 个基准币/多币同时启用：Lead 选币与 Main 使用同一策略规则，但资产/订单完全隔离。
- [ ] 策略 LONG/SHORT/CLOSE_LONG/CLOSE_SHORT 完整分支。
- [ ] 禁止新开仓时：已有 Managed 退出仍检查；既无仓位又无信号时不产生无用 REST。
- [ ] 旧订单待结算时不得再次 BUY/SELL 重复下单。
- [ ] WS 断线、行情过期、白名单失效、余额不足、时钟偏差和异常状态：**安全失败**，不伪造成功。
- [ ] 多币调度不重入；无真实交易所写请求；模拟决策与账本状态可核对。

### 验收标准

能在本地用同一套主合约策略，得到可复现的 Lead 开仓/退出信号与**模拟订单意图**；无 Main/Lead 串号；不会因关闭新开仓而丢失已有持仓退出判断。形成 `CODE_REVIEW_Lead-02.md`。

## 四、阶段 3：真实交易执行器与订单闭环（Lead-03）

### 目标

只针对 Lead 新增最小的生产交易适配器，**复用主合约已有订单、保护单、成交和 Ownership**，完成可验证的自动开仓→保护单→减仓/平仓→成交记录→对账→重启恢复。先由 Fake/Mock 与隔离环境验收，不能仅凭单测开启主网。

### 交易闭环（必须逐项打通）

1. **启用前校验**：Lead API Key 与真实 Portfolio 身份/权限验证、Hedge/Margin 模式、交易规则、资金、风控限额、WS 就绪、当前无未知订单；未满足则拒绝新的开仓。
2. **开仓**：LONG/SHORT 信号 → 幂等 ID → Lead 风控 → 账户专属 Binance Client 下单 → 订单确认 → 真实 Fill/Ownership 入库；提交结果未知时优先查单，不立即重复 POST。
3. **保护单**：对真实已成交仓位建立/维护与数量相符的 TP/SL，兼容当前 Binance Algo 接口；建单失败不得被“开仓成功”状态掩盖，需可恢复。
4. **退出**：CLOSE_LONG/CLOSE_SHORT、止盈、止损；只平本系统归属数量，处理部分成交、用户手动加减仓、撤单和保护单冲突。**关闭“自动新开仓”不阻止正常退出及对账**。
5. **异常恢复**：WS 掉线、REST 超时、429/418、重复消息、重启、订单未知状态 → 查订单及成交 → 恢复未结状态；保证不重复开仓、不误平仓。
6. **UI/数据库**：现有 Lead 持仓、订单页面显示真实记录及可解释错误；不新增第二张“影子订单”或手动审批表。

### 安全边界

- **只能给已验证的 Lead 账户下单**；绝不回退 Main 账户 API Key。
- 解除只读 Broker 的操作必须有**完整、可测试的真实交易接线和唯一启动条件**，不允许简单删掉 `ErrLiveExecutionLocked` / `LeadDurableOpenGate` 的拒绝逻辑来跳过资格验证。
- 生产启用权最终收敛为**单用户的一次明确配置/启用操作**，不是多层审批流；默认关闭，不会因部署新版二进制而自动下单。
- 新开仓暂停只控制 LONG/SHORT；已存在的 Managed 仓位在可信行情、账户和成交证据齐全时继续退出/维护保护单。若 WS/身份未知，则不得静默猜测仓位；安全停单并提示，需要重新核实。
- 审计只保留必要的**订单状态、Fill、风险阻断原因和恢复记录**，不用额外搭建审批/操作治理平台。

### 端到端测试矩阵

| 场景 | 必须验证 |
| --- | --- |
| LONG、SHORT 独立开仓和平仓 | 两种仓位方向与对应保护单、PnL/Fill 记录正确 |
| 部分成交与重复事件 | 成交数量、持仓数量和保护单一致，不重复入账 |
| 手动加仓/减仓 | 不把手动仓位当 Managed，平仓数量不超过真实可归属数量 |
| 停新开仓时已有仓位 | 不再开新仓，正常退出/撤改单与对账仍运作 |
| 下单超时/断开 | Unknown → 查询 Binance → 恢复；禁止双重开仓 |
| 429/418 与订单配额用尽 | 暂缓新开仓；优先保留正常保护/平仓能力，但不能突破交易所硬限额 |
| 进程重启/WS 重连 | 账户隔离与订单归属恢复，未结订单不会被视为新单 |
| 双账户同时运行 | Main 原行为不变；Lead 无任何跨账户读写 |

### 验收标准

Fake/Mock 完整走通；隔离联调证明所有写请求都带 Lead 凭证且绝无 Main 回退；通过 `go test`、`-race`、关键故障回归。若 Binance Testnet 不支持真实 Lead Portfolio 功能，应将缺口明确列为**待主网只读核验**，不得以 Testnet 的普通合约账户冒充真实 Lead 资格。形成 `CODE_REVIEW_Lead-03.md`。

**此阶段“代码闭环”不等于“主网真实资金允许自动开仓”。**

## 五、阶段 4：API 限额、真实验收与部署（Lead-04）

### 目标

在 Main + Lead 并行环境验证限额与恢复成本；完成只读资格检查、策略链路、订单/保护单的真实环境验收。**最终实盘启用必须由用户单独明确决定**，不能因为文档或自动化测试通过就自动启用。

### 限额方案（复用现有组件）

1. **共享限制**：继续使用 `service/binanceapiusage` 的 Futures 全局 IP Weight、订单计数和 429/418 退避，不建立第二套互不知情的全局预算。
2. **Lead 独立订单预算**：保留 `lead_order_limiter.go` 的保守本地配额（当前普通开仓 16/10s，高优先级 18/10s），真实限制以 Binance 返回值和 API 文档为准；开仓不得挤占平仓/撤单资源。
3. **SAPI 统计补全**：核对 `/sapi/v1/copyTrading/*` 的实际 IP/UID Weight 响应头，与 Futures REST 分开观测，不能因为 `Product=futures` 就把 SAPI 的权重统计当作准确。
4. **行情/账户请求去重**：复用 WS 及共享行情/K 线缓存；完整账户快照在一个轮次内复用，设短 TTL 和过期/身份校验；执行前仍刷新关键持仓和资金；不每 2 秒对每个币调用一次全量 `GetIncomeHistory`。
5. **异常退避**：WS 未就绪、未知订单、429/418、SAPI 白名单刷新失败时做有界退避；不通过连续快速重试刷接口；保留原有“异常要人工复核”的识别。
6. **看板监测**：只需要已有系统看板展示 Main/Lead 请求数、Weight、429/418、订单数、最近异常和 WS 健康；不新增独立监控平台。

### 必须产生的数据证据

- [ ] Main 单独运行、Lead 单独运行、两者并行的 `1m/5m` REST 请求数、端点分布、估算和实测 `USED-WEIGHT-1M`。
- [ ] Binance 返回的订单次数、SAPI IP/UID 计数与系统统计差异。
- [ ] 10/30/60 候选币扫描的每轮时长 P50/P95、缓存命中率、已管理仓位的退出检查延迟。
- [ ] 人为注入 429、418、网络超时、WS 断线、部分成交时的实际退避、订单归属恢复与请求量。
- [ ] MySQL 8 `EXPLAIN`/P95：Lead 活动/历史持仓与 Fill 查询，避免每轮无界回放历史全表。
- [ ] ARM Linux 构建、数据库 Schema v25（或当时目标版本）物理结构检查、服务启动/重启/回滚检查。

### 发布 Gate

| Gate | 要求 |
| --- | --- |
| 只读资格 | 真实 Lead Portfolio、账户 API 权限、签名 WS 与 SAPI 白名单必须经权威读请求验证；不使用 Portfolio 标签代替身份 |
| 数据完整性 | 未知订单归属、未结算 Fill、手动仓位和保护单状态均可被发现并阻断危险下单 |
| 交易安全 | LONG/SHORT、TP/SL、部分成交、暂停开仓后平仓、重复请求与重启恢复全部通过 |
| 限额 | Main/Lead 双账户负载有观测证据，没有无限重试或明显高权重轮询 |
| 人工部署 | 用户核对生产凭证/数据库/配置后，按现有流程发布；**默认关闭新开仓**；小额真实交易需再次明确授权 |

### 验收标准

形成可复现的压测/回归报告和 `CODE_REVIEW_Lead-04.md`；只对完成授权的环境执行真实交易试验；报告明确区分模拟、Testnet、主网只读和主网真实成交证据。失败立即保持开仓关闭，并记录未完成项目供下一轮修复。

## 六、跨阶段共同约束与实施原则

### 必须保留的正确性保护

- Lead/Main 的 API 凭证、资产、订单、WS、信号执行器和 Owner 作用域隔离。
- Binance 真实 Fill 归属、`clientOrderId` 幂等、订单未知状态查询、真实价格/数量过滤器、TP/SL、异常恢复。
- 429/418 退避与全局 Weight 限制；已管理仓位退出优先于无持仓新开仓。
- 开仓开关关闭后**不立即强制平仓，也不丢弃已有持仓的退出与对账工作**。
- 严格禁止生产 DB 写入作为开发测试；服务器正式 Schema 只按审批后的既有同步步骤执行。

### 明确不做

- 不引入审批工作流、操作审计数据库、额外审批页面、独立 AI 代理交易决策或多租户 RBAC。
- 不复制 Main 的选币/指标/策略模板/订单数据库体系；仅加账户绑定适配。
- 不增加 MarketCondition、Benchmark 或时间窗口作为新的交易过滤器。
- 不因精简而删除交易所幂等、真实 Fill、风控底线或异常恢复。
- 不为未完成的旧 Lead 配置编写兼容或迁移；无引用代码可以直接删除，但不得自动删除真实交易订单/Fill/凭证证据。
- 不在阶段 1/2/3 自动开启主网真实订单，不以 Mock 测试结果冒充实盘验收。

### 开发执行规则

1. **严格 Lead-01 → Lead-02 → Lead-03 → Lead-04**，每阶段开发、专项测试、`CODE_REVIEW_Lead-0X.md` 后才进入下一阶段。
2. 只修改必要的 Go/Vue 代码；前端变更后执行 `pnpm build` 并同步 `dist/` 至后端 `static/`，同时更新中英文文档。
3. 默认测试数据库、Mock/Fake 交易所；正常 `go test`、专项 `-race`、`go vet`；对意外失败不通过删测试“解决”。
4. 数据库 Schema 变化须单独列出 SQL/版本及回滚，不迁移未完成的旧 Lead 数据，不修改 `app.conf` 连接或直接操作生产库。
5. 发生策略、账户或资金安全分歧时，以“**不多开、不误平、不跨账户、不伪造交易所成交**”优先，而不是追求让程序表面继续运行。
6. 每阶段产出：变更文件清单、删除/复用清单、测试结果、当前尚未闭环的真实交易限制、下一阶段入口条件。

## 七、最终交付定义

完成四阶段后，用户只需配置一份独立 Lead 凭证、合理的 Lead 单笔/总风险额度及一个“自动新开仓”开关；Lead 使用同一套主合约选币/开平仓策略，但由独立账户真实执行，形成完整可查询的订单和 Fill 账本。

**验收时必须能够解释：每轮选了哪些币、为什么开/不开、已有仓位何时平、每笔单由哪个账户提交、Binance 是否成交、保护单是否存在、失败后如何恢复，以及运行过程中消耗多少 REST Weight。**

如果无法回答上述问题，就算前端页面、风控配置和 Mock 测试全部完成，也不能认定“合约带单已开发完成”。
