# 方案 05：合约加仓（个人版）

状态：设计稿，尚未实现。
优先级：P2，先完成方案 01；推荐在方案 04 多空双开之后做。
目标：已有仓位可以按**独立自定义加仓条件**继续同方向买入/卖出；真实成交多少就增加多少，保留平均成本、剩余数量和风控。
原则：**不新建仓位周期表、不做网格/马丁倍投、不重写整个交易引擎。**

## 1. 现有代码可以复用什么

- `feature/feature.go`：目前开仓要求 `hasPositionLong/Short == false`，且整个币种受 `openBlockedSymbols` 限制；需要新增**单独的加仓判断分支**，不是删除原开仓检查。
- `feature/trade_cycle_snapshot.go`：当前只记录“有没有某方向仓位/挂单”，加仓需要读该方向**准确的已成交数量**、活跃挂单与当前预算。
- `service/futuresownership/service.go`：`ensureSlotAvailable` 防止同方向重复 OPEN；已有 `ApplyFill` 能按累计成交增量更新 `ManagedQty` 和加权 `EntryPrice`。**重点复用这段，扩展 IntentAdd 即可。**
- 旧 `models.Order` 只有一对一开平关联，不能再用它解释加仓历史；方案 01 的 `futures_trade_fills` 负责成交事实。
- 当前 `SubmitClose` 收到 ACK 就记录全量平仓的旧行为必须先修复，否则加仓后平均成本/利润数据会更不准确。

## 2. 一期的功能限制（故意保持简单）

- 仅 USDM 主账户的 `auto_strategy`、单币同方向、单一持仓归属；不扩展 Lead/手工持仓。
- 自定义策略新增 `add_long` / `add_short`，**旧策略没有这两种规则就永远不会加仓**。
- 最多加仓次数可配置：建议默认 0（关闭），启用后先限制为 1～2 次。预算和初始开仓金额分别设置。
- 每次加仓固定金额，不做动态倍数、亏损越多越加、自动改杠杆、跨币调整保证金。
- 同一方向存在未成交开仓、加仓、平仓、未知订单或保护单异常时，拒绝新加仓。
- 加仓成功后原有止盈止损按**已确认新仓位**重新计算/调整，不因为加仓忘记保护仓位。
- 单向模式可以先支持，同方向要带 positionSide，避免日后 Hedge 需要再次重构。

## 3. 最少代码变更

### 3.1 策略层

在现有自定义策略类型校验及 `line_custom` 里增加：
- `add_long`：必须有策略归属 LONG 仓位且没有待处理订单；
- `add_short`：必须有策略归属 SHORT 仓位且没有待处理订单；
- 策略变量尽量沿用 `Position`、`ROI`、`NowPrice`；如确实需要 `AddCount`，只加一个受控变量，不建立新的策略 DSL。
- 加仓信号使用闭合 K 线时间 + strategy_hash + symbol + side 构造确定的标识/客户端订单 ID；同一 K 线重复触发不能重复提交。K 线或状态无法确认时跳过本次加仓。

### 3.2 持仓 / Ownership 层

- 在 `futures_managed_orders.intent` 增加 `add`，继续使用相同的 ClientOrderID 唯一约束与 DB 预留逻辑。
- `ClaimOrder` 对 `IntentAdd` 的校验：必须存在本人归属的同向 active 仓位；持仓数量与账户快照一致；当前没有活跃 ADD、CLOSE 或需要对账的订单。
- 现有 `ApplyFill` 的 ADD 增量走开仓方向的加权平均成本逻辑，不能改“普通 OPEN 已有仓位时拒绝”的规则。
- 加仓次数可从该 owner、symbol、side 的已成交 ADD 订单统计；如频繁查询有性能问题，再加一个简易缓存/单列，不先增加仓位周期表。
- 实际成交部分仍在方案 01 的 `futures_trade_fills` 存单笔记录，用 trade_id 去重；没有实际成交不增加加仓次数/持仓数量。
- 若目前一个 Owner 可能存在多次先平仓再重新开仓，统计加仓次数时需用已有持仓记录的“本轮开仓时间/ID”限定，不能跨历史生命周期累计；只有现有字段不足时再增加一个 `entry_ref`，不新建整套 cycle 模型。

### 3.3 风控与退出层

- 保持已有合约最大仓位数限制，额外检查：本币方向的最大名义金额、此次加仓预算、累计加仓次数、可用保证金、当前杠杆、持仓数据是否可对账。
- 实际保证金风险按已有持仓 + 所有未成交/正在提交 ADD 的最大可能新增量计算，不仅看已成交数量。
- 部分平仓/有保护单即将触发时禁止加仓；止损优先于加仓。
- 加仓后用交易所真实新持仓数量/已成交记录更新退出策略的成本和 ROI；平仓还是按已确认可管理剩余量。
- 如果保护单调整失败，记录异常并暂停该方向新增风险；**不能**因为保护单失败就把已经实际成交的 ADD 删除。

## 4. 例子（必须在单测中重现）

初始 LONG 2 @ 100。请求再加 3：
- ADD 实际分两次成交：1 @ 110、1 @ 112，最后 1 撤单；
- 当前实际仓位：4，平均成本 `(2×100 + 110 + 112)/4=105.5`；不是开仓 5；
- 加仓次数计 1 次（这笔 ADD 意图实际有成交），不是按两笔 Fill 计 2 次；
- 接着请求平 4，只成交 1 @ 120：实际剩余 3、已实现毛收益按 1×(120−105.5)=14.5 计算（未扣费、适用于该 USDM 线性多仓示例）。
- 同一笔成交 WS 重复送 10 次，实际仓位和累计收益也不得变化。

## 5. 实施步骤（三步）

**P1：最小数据支持**
- 增加 `IntentAdd` 与 Owner 验证，保持旧 OPEN 的安全限制；
- 若方案 01 尚未实现真实 Fill 记账，**本阶段不允许打开加仓实盘**；
- 扩充测试数据，核验多次开仓量和方向平均价。

**P2：策略入口与风控**
- `feature/feature.go` 增加与现有首次开仓并列的 add_long/add_short 分支，独立策略条件、金额、次数和风险校验；
- 对已有挂单/待平仓单做简单阻挡，使用持久化唯一信号标识防重复下单；
- 调整止盈止损和退出判断，按实时管理数量更新。

**P3：页面与验证**
- 在现有合约币种配置增加“允许加仓、每次金额、最多次数”三个主要配置；默认禁用；
- 在现有订单列表通过 `intent=add` 显示加仓订单，持仓详情增加“平均成本、已加次数、当前数量”，不用做多层加仓管理后台；
- 测试部分成交、取消、重复 WS、数据库故障、重启、同币多空另一腿隔离；再由用户决定小额启用。

## 6. 不做及验收要求

不做：网格、倍投马丁、每层独立 TP/SL、自动再平衡、多策略同时持有同方向同币资产、跨账户风险中台、独立资金流水表、复杂 FIFO/LIFO 仓位匹配。

验收：
1. 无 add_* 的旧策略行为不变。
2. 同向有仓且 add 条件满足时允许**仅一次合法**增量委托；没有仓位不能 ADD。
3. 计划加 3 实成 2，仓位只增 2；重复 fill 不增仓。
4. 手工/未归属仓位、不同 owner、相反方向都不能被误加。
5. 部分平仓后净数量、成本和收益可信，挂单与保护单数量不会超量。
6. 一旦不能确认订单或管理量，停止继续加仓；现有安全平仓和人工处理保留。
