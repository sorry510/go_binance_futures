# 合约自动交易仓位/订单归属隔离改造计划

> 状态：规划完成；本次只实施第 1 步“开启合约交易风险确认弹窗”。
> 目标：真实自动交易只能修改明确由对应系统模块创建并归属给该模块的仓位和订单，绝不能因为账户里存在仓位/挂单就自动接管。
> V3 对应阶段：`doc/agent/v3/05-phase-v3-5-trade-safety.md`。本文件是 V3-5 的 **ownership 详细设计真相源**；V3-5 Phase 文档负责实施顺序与 Gate，如出现 ownership 细节差异，以本文件为准。

## 1. 问题等级与结论

当前问题按真实资金安全应视为 **P0 / Critical**。

`main.go` 每 2 秒调用一次 `feature.StartTrade(&SystemConfig)`。只要 `FutureEnable == 1`，主自动交易会读取账户级仓位和账户级未完成订单，而不是读取“本系统创建的仓位/订单”。

当前唯一的保护条件是 `FutureExcludeSymbols`（前端“排除自动交易的币”）。因此，只要币种没有进入排除列表，手工交易、其它机器人或其它系统模块创建的仓位/挂单都可能被主自动交易修改。

已确认存在两类直接资金风险：

1. **误平仓**：`StartTrade` 对账户全部非零仓位执行 AutoStopOrder、止损、止盈判断，满足条件后直接调用 Binance 市价单平仓。
2. **误撤单**：`cancelTimeoutOrder` 对账户全部未完成合约订单检查超时，满足条件后直接调用 Binance CancelOrder。

所以本次改造不能只解决“平仓识别”，必须同时解决 **仓位 ownership** 和 **订单 ownership**。

## 2. 当前真实交易链路核查

### 2.1 配置开关

- 前端：`go_binance_futrues_new_ui/src/views/dashboard/configShow.vue`
- 后端读取/保存：`controllers/index.go` 的 `GetServiceConfig` / `EditServiceConfig`
- 配置字段：`models.Config.FutureEnable` → DB `config.future_enable`
- 后端每 2 秒通过 `updateSystemConfig()` 刷新 `SystemConfig`

### 2.2 主自动交易

`feature/feature.go::StartTrade` 的当前顺序：

1. 检查 `FutureEnable`。
2. `GetAllSymbols()` 获取策略币种。
3. `GetTransformPositions()` 获取当前账户全部非零仓位。
4. `getTransformOpenOrders()` 获取当前账户全部未完成订单。
5. 生成 `FutureExcludeSymbols` 排除集合。
6. `cancelTimeoutOrder()` 撤销非排除币种的超时订单。
7. 遍历所有非排除仓位，执行自动止损/止盈/策略反转平仓。
8. 再以账户仓位/挂单判断是否允许继续开新仓。
9. 系统新开仓成功后才通过 `insertOpenOrder()` 写入旧 `order` 表。

关键问题：第 6、7 步没有使用 `order` 表判断订单或仓位是不是由 `StartTrade` 创建。

### 2.3 仓位/订单数据源不是 ownership 数据

当 `ws::futures_user_data = 0` 时：

- `GetTransformPositions()` 直接调用 Binance `GetPosition()`。
- `getTransformOpenOrders()` 直接调用 Binance `GetOpenOrder()`。

当 `ws::futures_user_data = 1` 时：

- 读取本地 `futures_positions` / `futures_orders`。
- 但这两个表由 `feature_userdata.go` 和 `WsUserData()` 同步 **整个 Binance 账户**。
- 因此它们只是账户镜像，不代表“系统拥有”。

结论：无论 WS 本地模式还是 API 模式，当前风险完全一致。

### 2.4 旧 `order` 表不能直接作为 ownership 真相源

旧 `order` 表确实记录 `StartTrade` 的开仓和平仓历史，但目前存在以下限制：

- 只有主自动策略的 `insertOpenOrder()` 会写入，系统其它真实合约入口没有统一写入。
- 限价单写入的是下单数量，不等于最终成交数量，存在未成交/部分成交状态问题。
- 开仓和平仓的关联依赖 symbol + amount + positionSide + orderId 顺序匹配，不是稳定的 ownership ID。
- `UpdateOrderStatus()` 对是否仍有仓位的判断只比较 symbol，连 LONG/SHORT 都没有区分。
- 该表主要承担历史/统计用途，不适合作为实时仓位归属账本。

因此建议保留 `order` 表作为历史统计兼容表，但不要把它升级成唯一 ownership 真相源。

### 2.5 其它真实合约开仓入口

代码中还存在多条可产生真实 Binance 合约仓位的路径：

- `feature/feature_rush.go`：合约抢新。
- `feature/feature_notice.go`：币种提醒触发自动下单，并可能附带止盈/止损条件单。
- `feature/feature_listen.go`：资金费率监听自动开多/开空。
- `service/agenttrade/default.go`：Agent 受控交易，通过独立 `ClientOrderID` 下单。

这些入口目前没有统一 ownership 模型。主 `StartTrade` 会看到它们产生的账户仓位，并可能按自己的策略平掉。

因此最终模型必须支持 owner，而不能只有 `is_system = 1`：不同系统模块之间也必须隔离。

建议 owner 至少包含：`auto_strategy`、`new_coin_rush`、`notice_auto_order`、`funding_rate`、`agent_trade`。

## 3. 目标架构原则

### 3.1 Observation 与 Mutation 分离

系统仍然允许读取整个 Binance 账户，用于：

- 判断同 symbol/positionSide 是否已存在手工仓位，避免混仓。
- 判断账户总风险、保证金和总暴露。
- 判断是否已有手工挂单，避免重复开仓。

但任何会修改 Binance 状态的操作必须先通过 ownership 校验：

- 平仓：只能减少本 owner 的 managed quantity。
- 撤单：只能取消本 owner 创建并登记的 exchange order。
- 修改订单：只能修改本 owner 订单。
- 主自动策略不得处理其它 owner 的仓位/订单。

### 3.2 Fail Closed

ownership 无法确认时一律视为 **unmanaged**：只读、不平、不撤、不改单。

系统升级后，不允许根据“当前账户存在仓位”自动认领历史仓位。旧仓位默认全部 unmanaged，避免上线瞬间重新产生误平仓。

### 3.3 “排除自动交易的币”继续作为最高优先级保护

`FutureExcludeSymbols` 保留，并位于 ownership 校验之前：

- 排除币不创建新的 `auto_strategy` 仓位。
- 即使已经是 managed position，也暂停自动平仓。
- 即使已经是 managed order，也不执行自动撤单。
- 从排除列表移除后，可继续按照原 ownership 恢复管理，不自动丢失归属。

## 4. 建议的数据模型

不要给 `futures_positions` 增加简单 `is_managed` 字段，因为该表是账户镜像，会被 API/WS 全量同步覆盖，而且无法表达 managed quantity、owner、订单来源和生命周期。

建议新增独立 ownership 数据：

### 4.1 `futures_managed_positions`

建议字段：

- `id`
- `owner`：`auto_strategy` / `new_coin_rush` / `notice_auto_order` / `funding_rate` / `agent_trade`
- `symbol`
- `position_side`：LONG / SHORT
- `managed_qty`：系统当前有权管理的数量
- `entry_price`：归属仓位的参考开仓价
- `status`：active / suspended / closed / reconcile_required
- `source_ref`：关联策略、Proposal 或业务记录 ID
- `created_at` / `updated_at` / `closed_at`

同一个 `(symbol, position_side)` 建议同一时间只允许一个 active owner。Binance Hedge Mode 下同方向仓位最终会聚合；禁止多个 owner 同时拥有同一方向，可以显著降低归属歧义。

### 4.2 `futures_managed_orders`

建议字段：

- `id`、`owner`、`symbol`、`position_side`
- `intent`：open / close / take_profit / stop_loss
- `client_order_id`、`exchange_order_id`
- `requested_qty`、`filled_qty`
- `order_type`、`status`
- `source_ref`、`created_at`、`updated_at`

所有系统真实订单都应先生成可识别的 `ClientOrderID`，并持久化归属，再提交 Binance。这样进程崩溃或 WS 丢事件后仍可恢复订单身份。

## 5. 仓位数量与人工操作的安全规则

ownership 不能只记录“这个币属于系统”，必须记录 `managed_qty`。

原因：用户可能在 Binance 手工对同一 symbol/positionSide 加仓或减仓，交易所最终只返回聚合仓位。

建议每轮 reconciliation 使用以下规则：

1. `account_qty == 0`：managed position 标记 closed/external_closed，系统不再尝试平仓。
2. `0 < account_qty < managed_qty`：认为发生了外部减仓，把 `managed_qty` 下调到 `account_qty`，绝不补仓，也绝不按旧数量平仓。
3. `account_qty > managed_qty`：认为多出的数量可能来自人工加仓，`managed_qty` 保持不变；自动平仓最多只允许提交 `managed_qty`。
4. 没有 managed record 的账户仓位：永远 unmanaged，不进入自动止盈/止损执行。
5. 没有 managed record 的账户挂单：永远不能由 timeout cancel 逻辑撤销。

主自动交易在平仓前应再次以最新账户仓位做一次数量夹取：`close_qty = min(managed_qty, current_account_qty)`，并在成功成交后按实际成交量减少 `managed_qty`。

### 5.1 开仓冲突规则

如果账户已经存在同 `(symbol, position_side)` 的 unmanaged 仓位，`auto_strategy` 不应再对同方向开仓，否则会在 Binance 聚合后失去清晰边界。

如果其它 owner 已拥有同 `(symbol, position_side)`，也应拒绝新的 owner 开仓。后续如果确实需要多 owner 共仓，应另做显式净额账本，不在本次安全改造范围内。

## 6. 对现有主交易流程的目标修改

`StartTrade` 最终应同时持有两类视图：

- `accountPositions/accountOpenOrders`：全账户只读视图，用于风险和冲突检查。
- `managedPositions/managedOrders(owner=auto_strategy)`：主自动交易可写视图。

目标行为：timeout cancel 只遍历 `managedOrders`；自动平仓只遍历 `managedPositions`；开仓前仍检查全账户是否已有冲突仓位/挂单。

## 7. 分阶段实施计划

### 第 1 步：开启合约交易风险确认（本次实施）

范围仅限前端配置页：

- 用户从关闭切换到开启时弹出 warning 确认框。
- 文案明确说明：当前账户所有合约仓位和挂单都会由自动交易系统管理，排除列表中的币种除外。
- 点击取消：不开启，不调用保存接口，开关保持关闭。
- 点击“确定打开”：才保存 `future_enable = 1`。
- 从开启切换为关闭：不弹确认，直接关闭，避免阻碍紧急停机。

注意：这一步只是当前危险行为的显式告知，**不解决根因**。

另外存在一个重要旁路：`feature_test_strategy.go::autoTestToTrade()` 在测试策略连续盈利达到 `FutureTestAutoTradeCountLimit` 时会直接设置 `FutureEnable = 1`，不会经过网页确认。按本次范围不修改，但在 ownership 改造完成前仍属于残余 P0 风险。

### 第 2 步：建立 ownership 数据模型与服务层

- 新增 managed position / managed order 模型和 DB schema。
- 建立 OwnershipService，统一提供 claim、fill、reduce、close、suspend、reconcile 查询。
- 先以 shadow 模式记录和校验，不改变现有交易执行结果。
- 对 ownership 缺失、冲突、数量异常输出明确日志和可观测事件。

### 第 3 步：统一系统开仓登记

- 主 `StartTrade` 的 MARKET/LIMIT 开仓全部通过 ownership-aware execution service。
- 为系统订单生成唯一 ClientOrderID。
- 以 Binance 实际 fill quantity 更新 managed quantity，而不是仅使用请求数量。
- 部分成交、撤单、失败必须有明确状态机。

### 第 4 步：切换主自动交易的修改边界

- `cancelTimeoutOrder` 改为只处理 `owner=auto_strategy` 的 managed orders。
- 自动止损/止盈/AutoStopOrder 改为只处理 `owner=auto_strategy` 的 managed positions。
- `FutureExcludeSymbols` 继续优先跳过。
- 平仓数量不得超过 `managed_qty`。
- 全账户仓位仍用于冲突检查和账户风险计算，但不获得修改权限。

### 第 5 步：重启恢复与 reconciliation

- 启动后先同步 Binance 账户镜像，再恢复 ownership。
- 当前账户已有但没有 managed record 的仓位/订单全部保持 unmanaged。
- 禁止从旧 `order` 表或账户现状自动认领真实仓位。
- 处理人工部分平仓、人工加仓、订单部分成交、WS 断线/API 补偿等场景。
- `UpdateOrderStatus()` 改为基于 ownership/exchange order ID 对账，不再使用 symbol-only 判断。

### 第 6 步：其它真实交易模块 owner 化

逐个接入：

1. `new_coin_rush`
2. `notice_auto_order`
3. `funding_rate`
4. `agent_trade`

每个 owner 只能修改自己创建的订单/仓位。主 `StartTrade` 不得替其它 owner 执行退出逻辑。各模块如果需要止盈/止损，应由自己的 lifecycle 明确定义。

### 第 7 步：移除临时风险文案并完成切换

ownership 隔离上线并验证后，当前第 1 步的警告文案应更新，因为“开启后账户全部合约都会被管理”将不再符合事实。

届时 UI 应改成：开启后仅管理自动交易系统自己创建且归属为 `auto_strategy` 的仓位/订单，手工仓位不会被接管。

## 8. 必须覆盖的验收场景

### 8.1 第 1 步 UI 验收

- `FutureEnable=0`，点击开启：必须出现 warning。
- warning 出现前不得发送 `PUT service/config`。
- 点击取消：`future_enable` 保持 0。
- 点击确定：发送 `future_enable=1`，刷新后仍显示开启。
- `FutureEnable=1` 点击关闭：不弹窗，直接保存 0。

### 8.2 ownership 最终验收

- 手工 BTCUSDT LONG + 自动交易开启：不得平仓。
- 手工超时 LIMIT 挂单：不得被 `cancelTimeoutOrder` 撤销。
- `auto_strategy` 创建 ETHUSDT LONG：策略满足退出时允许平仓。
- 人工在 managed ETHUSDT LONG 上加仓：自动系统最多平自己的 `managed_qty`，人工增加部分必须保留。
- 人工部分平掉 managed position：系统自动下调 managed quantity，不得重新补回，不得按旧数量过量平仓。
- managed symbol 加入 `FutureExcludeSymbols`：不得自动平仓/撤单。
- 重启服务：ownership 仍可恢复，不能把其它账户仓位认领进来。
- WS 本地仓位模式和直接 API 模式行为必须一致。
- 限价单部分成交后，只把实际成交数量计入 managed position。
- Agent 创建的仓位不得被 `auto_strategy` 平仓。
- 同一 `(symbol, position_side)` 已存在 unmanaged 或其它 owner 仓位时，新 owner 开仓应被安全拒绝。

## 9. 本次实际修改边界

本次只实现第 1 步，不修改：数据库 schema、`StartTrade`、平仓逻辑、撤单逻辑、ownership、测试策略自动切换、Agent 交易或其它真实下单模块。

这意味着在后续 ownership 改造完成前，风险确认框只能防止用户在网页上无意识开启；直接 API 修改或测试策略自动切换仍可绕过该提示。

## 10. 后续改造重点文件

当前已核查并需要在后续阶段重点处理的文件：

- `main.go`：配置刷新、2 秒主自动交易调度。
- `feature/feature.go`：StartTrade、全账户仓位/订单转换、超时撤单、开平仓历史。
- `feature/feature_userdata.go`：账户仓位/订单 API 镜像同步。
- `feature/api/binance/index.go`：用户数据 WS 对 `futures_positions` / `futures_orders` 的全账户同步。
- `feature/order.go`：旧 order 历史状态兜底同步。
- `models/tableStruct.go`、`models/futures_postions.go`、`models/futures_orders.go`：现有数据结构。
- `feature/feature_rush.go`：合约抢新真实下单。
- `feature/feature_notice.go`：价格提醒自动下单及 TP/SL 条件单。
- `feature/feature_listen.go`：资金费率自动真实下单。
- `service/agenttrade/default.go`：Agent 受控交易真实执行。
- 前端 `src/views/dashboard/configShow.vue`：合约交易开关和排除币配置。

原则上后续不应继续让各模块直接散落调用 Binance 下单接口；应逐步收敛到统一的 ownership-aware execution service，确保“创建订单 → 记录 owner → Binance 提交 → 成交回报 → managed quantity → 退出/撤单”形成一条可恢复、可审计的生命周期。
