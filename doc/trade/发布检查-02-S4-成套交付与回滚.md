# 02-S4 成套交付、验收与回滚 SOP

更新：2026-11-10  
状态：**仅为发布方案，不表示已获生产授权或执行过生产部署。**

## 一、不可拆开的交付单元

- **Schema**：当前二进制唯一版本真源 `appversion.DatabaseSchemaVersion = 25`；生产实际版本必须单独只读核实，不得因为 README、static 或本地 SQLite 测试通过就默认完成迁移。
- **后端二进制**：必须包含 `routers/router.go` 新增的 S4-R5 四条 GET：`/spots/symbols`、`/spots/strategy/holdings`、`/spots/strategy/orders`、`/spots/strategy/fills`，以及 S3-R1 的实盘编译期硬封锁。记录 Git SHA、Go 构建输出 SHA-256。
- **前端 `static/`**：必须由匹配该后端接口契约的 Vue `pnpm build` 输出，记录构建时间、提交 SHA、全部文件相对路径+SHA-256，核对 `index.html` 引用资源和 `spotStrategy-*.js` 存在。
- **发布/回滚记录**：记录操作者、时间、当前生效版本、旧包和新包的哈希、数据库备份可恢复性与上线后只读核验结果。**前端文件独立复制不构成完整发布**。

## 二、正式部署前强制 Gate（目前都未批准）

1. 明确获得用户对**生产数据库迁移**、**服务停止/重启/部署**的分别授权；真实 Spot 下单和撤单需要**另外**单独授权，本清单不授予交易权。
2. 先只读核对生产 Schema、旧币种/订单/库存、手动资产归属，梳理 S0/S3-R1 未决项；生产 MySQL 8 的表/索引、查询计划及异常恢复还没有验收，不得跳过。
3. 生成完整可回滚包，包含**旧版可执行文件 + 旧版 static 全目录 + 配置文件副本 + DB 全量一致性备份**。恢复演练必须确认备份能够在隔离环境正常打开。**不要修改现有 `conf/app.conf` 数据库连接配置**。
4. 在隔离环境完成本次候选包的 Go/Vue 自动测试、JWT 路由正反向 E2E、老现货通知/监听、旧合约订单回归、静态文件 manifest 比对。记录 **PASS / FAIL / SKIPPED / BLOCKED**，不得把自动化 SQLite Fixture 认作真实交易 E2E。

## 三、经授权后的成套替换顺序（尚未执行）

1. 将**后端可执行文件和整个 static 目录**预先放到单独版本目录/发布包，保留旧包；校验二者哈希和接口版本，提前生成回滚指针。**禁止先把新 static 覆盖到仍运行的旧后端进程**，否则 S4 新页面会报 API 404。
2. 在维护窗口停止旧服务；禁止同时保留两个使用同一交易账户的活跃交易进程。核实已授权的停机和交易风险处置。
3. 核对数据库版本，**仅在收到明确生产迁移授权后**，且在维护窗口内通过目标版本的 `./go_binance_futures sync db` 完成所需 Schema 同步。**不通过直接 SQL 升级版本，不修改 `app.conf`**。
4. 数据库健康/版本门禁通过后，整体发布**同一候选包**里的二进制与 `static/`；再启动唯一服务进程。静态目录最终完整性和主进程使用的二进制哈希必须与该候选包 manifest 一致。
5. 上线只读验收：登录，**单独**查询 `GET /spots/strategy/mode` 确认真实许可仍被禁用；新的 `GET /spots/symbols` 仅检验 JWT、不依赖 mode。Holding/Orders/Fills 三个只读接口用无 Account/Owner 参数的请求正常获取固定 `main/auto_strategy` 归属数据，同时对显式非法 Owner/Account 仍返回 400；未登录返回 401。核验 JSON/分页、中英页面资源、空 Holding、旧现货/合约页面和旧职责不回退。
6. 任何部署验证不通过，停止新版本；依据实际版本兼容性选择恢复方式。**若数据库已升至 v25，不能假设旧二进制可以直接读取新 Schema**。必须按先前备份执行数据库回滚/恢复与原二进制+static 成套回退，经数据核验后才重新启动旧服务。

## 四、当前严格禁止的操作

- 不用 `git pull`、单独 `rsync static/` 或只换前端 `index.html` 当成生产部署。
- 不从网页启用真实 Spot 委托/撤单或通过修改 `config.spot_auto_trade_mode` 绕过 S3-R1。
- 不将 `rest_verified=0` 人为更新为 1、伪造已核实 Holding/收益，或用测试 Fixture 冒充生产成交。
- 不自动执行生产 `sync db`、停止/重启服务、真实 Binance 请求、commit 或 push。

## 五、本轮审查结论

S4 目前只具备**离线只读接口、页面骨架及编译/隔离验证能力**。由于 S3-R1 的真实响应来源认证与持久化授权尚未通过，运行链路产生的 Fill 无法成为已核实 Holding；任何“持仓 E2E 已通过”的声明都不成立。完整浏览器人工 E2E、真实产物成套部署、数据库回滚演练和实盘审核，仍各自独立 **BLOCKED**。


### 02ALL 更新：防止“半发布”和错误的全量验收口径

`s3_legacy_preflight.go` 已在普通编译中排除，仅用于 `spot_legacy_doctor` tagged 离线诊断。新前端不再调用交易 mode 接口以展示本地账户，但**必须确认 Go 二进制包含 S4 当前接口并正确执行 JWT/内部 Owner 过滤**；这不是允许跳过二进制与 `static` 同版本发布。旧本地运行 PID/3333 的历史风险与今天的运行状态应分开记录，不能由本地 dist/static 相同推断线上已更新。

完整 `go test ./...` 曾存在与 S4 无关的 controllers fixture 红点和需要保密 `conf/app.conf` 的 tests 包；只有带明确包清单与 PASS 证据的离线检查可称为通过，不能写全仓 PASS。详见 [02ALL 复审](CODE_REVIEW_02-ALL-rereview.md)。
