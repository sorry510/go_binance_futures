## 二、统一边界与基线

1. 保留 Go 技术指标 + Technology JSON + Expr Strategy JSON 架构，复用现有 `service/strategy/expr_cache.go` 的 256 条 LRU 编译缓存；不引入 CEL、其他 DSL、Redis、外部服务或新调度器。
2. 仅优化性能。不统一策略执行器、策略变量、平仓规则、模板保存校验或运行诊断；不修改策略模板格式、开平仓条件、规则优先级、ROI 门槛、交易周期、仓位归属及订单执行语义。
3. 首先覆盖 U 本位 Main 自定义策略的实盘与模拟盘。Lead、现货和 COIN-M 使用共享代码时保持原有数据源、账户隔离及语义；未验证兼容前保持原调用方式。历史回测已有自己的指标/编译优化，原则上不改引擎，仅在证明收益且兼容时复用不可变配置计划。
4. 不增加数据库表、不执行数据库迁移、不修改 `conf/app.conf`、不写生产数据库（含 go_bn_oracle1/go_bn_oracle2）、不真实下单、不部署服务器。无 UI 需求，不修改前端和 static。
5. 每个阶段先采集旧路径基线，再在相同输入、相同策略配置与测试参数下采集新路径结果。统计 ns/op、B/op、allocs/op、JSON 解析次数、指标计算次数、缓存命中率、SQL 查询次数、行情请求次数、P50/P95（有稳定端到端样本时）、并发和缓存内存上限。优先使用本地确定性 fixture、mock loader/SQL 和 Go benchmark；必要时 pprof。不得用合成微基准替代生产端到端结论。
6. 正确性优先：相同有效输入下规则命中、顺序、返回值、指标序列长度、错误处理和交易结果不变；任何有意改变的行为不属于本方案，需另行确认。

## 三、CS-P1：策略配置解析与执行计划缓存

### 目标

相同策略分配给多个币种，或每秒反复评估时，不重复解析相同 JSON、筛选启用规则、计算指标配置的结构性信息。现有 Expr 编译缓存继续使用。

### 修改范围

- `service/strategy/identity.go`、`expr_cache.go`；新增轻量计划缓存模块（例如 `strategy_plan.go`）。
- `feature/strategy/line/line_custom.go`、`parse_technology_config.go`。
- `feature/feature_test_strategy.go`；必要的共享调用兼容层与专项测试。

### 实施方式

1. 以实际 Technology JSON + Strategy JSON 的内容为身份，复用 `StrategySnapshotHash`（注意其对字符串首尾空白的处理）。不得仅以模板 ID、模板名或币种为键。兼容旧空配置和 null 行为；空 hash、非法 JSON 不得误命中其他计划。保存/替换模板后，下一轮使用新内容对应计划，无需额外手动清缓存。
2. `StrategyPlan` 仅包含不可变信息：已解析的配置、原始顺序的启用规则、开仓与各方向平仓规则索引、已验证的结构信息、需要的 K 线周期和原有输入长度（150 根基线、按指标预热扩大，最多 1500 根）。不修改规则优先级，不通过分组改变 LONG/SHORT 之间的首次命中顺序。
3. Technology 的静态校验和长度计算只做一次；保留依赖当前 symbol 的名称冲突等检查，不能将其错误地跨币种复用。计划中不保存 ORM 对象、当前行情、仓位、ROI、FundingRate、时间、策略执行结果。
4. 使用简单进程内有界 LRU，初始上限建议 256 个计划；并发读取安全、计划不可变，限制内存，允许冷缓存重建。不引入持久化缓存。相同 key 并发构建合并或确保最多保存一个有效对象；避免持锁计算大批量指标或执行 Expr。
5. 继续使用原 `CompileRule`。只有在证明实际环境类型和编译选项完全一致的情况下，才允许减少重复签名构建或复用计划中的编译引用；不得绕过现有环境签名。第一阶段不重构整个 Expr 执行器。
6. 旧公开函数继续兼容；优先增加接受已解析配置/计划的内部入口，原入口作为兼容包装。模拟平仓继续使用开仓记录保存的策略内容，实盘继续使用现有选择的配置，不改变快照语义。

### 必测与验收

- 相同配置跨币种、连续调用共享计划；规则/指标/启用开关变化立即产生新计划；模板同 ID 修改不命中旧计划。
- 非法 JSON、空/null、禁用规则、名称冲突和重复指标按旧路径处理；开仓首次命中顺序、各方向平仓和策略哈希保持一致。
- 并发读取、淘汰、冷启动、缓存容量上限及 race 测试通过。
- 以固定 N 次同配置评估为样本，证明 JSON 解析和静态计划构建由每次重复执行减少为每个缓存有效期内一次（并发冷启动按实际统计）；记录热缓存 CPU 与分配量对比。无法证明净收益的进一步缓存不实施。

## 四、CS-P2：实时技术指标计算优化

### 目标

减少未使用指标的计算，以及实盘、模拟盘对同一币种同一有效行情输入的重复计算。保持指标数学公式、预热、数组索引和形成中 K 线语义。

### 修改范围

- `feature/strategy/line/parse_technology_config.go`、`technology.go`、CS-P1 计划缓存。
- `feature/api/binance/market_data_guard.go`、`kline_ws_cache.go`（仅在需要可靠行情版本时增加薄接口）。
- 参考 `service/backtest/indicator_cache.go` 的 AST 和增量计算测试，不重写回测引擎。

### CS-P2-1：按需计算

- 使用 Expr AST 分析启用规则引用的指标和 K 线变量，在计划中保存保守的依赖集合。可按当前开仓/平仓方向选取实际需要的集合，但必须保留现有规则遍历顺序。
- 只跳过能够证明完全无关的指标。遇到动态访问、解析异常、未知依赖、整个指标对象被传参等不能证明安全的情况，回退原完整计算。
- 不能因为规则只引用 `kline_1h` 而删除该周期的加载；即使对应指标未直接使用，仍保留 K 线变量及原周期加载条件。首轮保留全配置计算出来的原 K 线输入长度，不为优化擅自缩短预热窗口（否则 EMA/Wilder 等结果可能不同）。
- 只在生产规则执行路径启用裁剪，保留调试、编辑器、模板校验、API 等需要完整环境的调用方式；若裁剪导致旧错误处理、字段或信号行为改变，回退完整路径。

### CS-P2-2：指标结果缓存

- 优先复用同一市场、同一 symbol、同一周期、同一有效输入长度、同一指标类型与完整参数、同一行情快照的计算结果。缓存键必须包含足以识别完整参与计算的 K 线窗口版本；参数、历史修订或 WS/REST 更新后立即失效。仅按周期开始时间或最新价格作为版本是不充分的。
- 不跨现货、U 本位、COIN-M 或不同数据源错误复用。实时与历史绝不共享可变指标结果；Main/Lead/模拟可在数据源和输入相同的情况下共享纯行情指标，不共享账户变量。
- 形成中的 K 线 `[0]` 与最后已完成 K 线 `[1]` 保持现有语义。相同 K 线周期内，价格、高低点、成交额、成交次数及主动买入字段变化也可能使指标失效。QPS 等依赖当前时间的衍生字段不可仅按 K 线版本缓存；单独按原逻辑构建或明确纳入有效时间身份。
- 优先让既有行情读取路径返回可验证的版本/不可变快照，仍经过原 freshness/REST 兜底逻辑；不能绕开行情有效性校验直接返回旧指标。无法取得可靠版本时重新计算。
- 仅缓存成功、完整且可安全复用的纯指标值。指标输出 slice 不得被后续更新或调用方修改；按需要使用不可变快照或复制。失败、不完整或陈旧数据不能作为成功缓存；遵守原错误处理。缓存采用有界内存 LRU/按字节预算淘汰，初期按实测条目大小设上限并记录，禁止无限增长。
- 同 key 并发请求可合并计算，避免全局锁覆盖网络 I/O 与指标计算。先采用完整结果复用；只有 profiling 证明仍有瓶颈，才对 EMA/RSI/ADX/ATR 等高频指标选择性移植增量算法，逐指标与原实现对照。无需全面改写指标库。

### 必测与验收

- 覆盖所有现有指标类型、不同周期、多个参数和不同预热长度。原路径与新路径逐字段、序列长度、浮点数（严格等值或事先声明的容差）对比，规则布尔结果和命中规则必须一致。
- 同一快照重复计算次数下降；新形成中 K 线、同周期成交变化、已完成 K 线切换、REST 补数/历史更正、参数变更、缓存淘汰后重新计算正确。
- AST 覆盖 `Data[0]`、`Data[1]`、切片、动态索引、对象传参、仅引用 K 线、多个方向规则和未知依赖保守回退。不得为提高命中率改变数据时效。
- 进行多币、多指标、实盘与模拟并发 fixture，记录命中率、指标计算次数、CPU、内存和行情请求量；缓存有实际收益且无明显冷路径退化才验收。若可靠行情版本或有效复用率不足，只交付已证实安全有效的按需计算/复用部分，报告原因。

## 五、CS-P3：减少重复数据库查询

### 目标

将交易周期已读取的有效行情、币种配置及相同语义的仓位数据传入策略环境，减少逐币重复 SQL 和线性扫描，不改变账户数据来源或交易判断。

### 修改范围

- `feature/feature.go`、`feature/account_trade_cycle.go`、`feature/feature_test_strategy.go`。
- `feature/strategy/line/line_custom.go`、`parse_technology_config.go`。
- 原有环境构建入口继续兼容监听、控制器、Spot/COIN-M 等调用方。

### 实施方式

1. 每轮已读取的 `allCoins` 建立 `symbol -> coin` 索引，保留原币种列表、筛选规则及顺序。模拟平仓和实盘已有仓位查找使用索引，仍包含未启用但需处理退出的币种。若存在重复 symbol，保留旧查找语义或回退原查找。
2. 新增接受已加载 symbol 行情快照的内部 InitParseEnv 入口，直接构建 NowPrice/NowSymbol*；策略 JSON、技术指标以及 FundingRate 仍按现有来源和 CS-P1/P2 逻辑处理。不要使用进程级长 TTL 缓存 ticker；使用已验证的新鲜度、与旧路径一致的字段映射及必要的局部刷新/回退。
3. 特别注意现有 InitParseEnv 是在评估时重新读取行情，复用轮初数据可能改变价格/触发时点。只有满足原行情时效要求且不会使信号使用过期快照时才复用；否则刷新当前 symbol（或批量刷新候选快照），不追求强制零查询。原下单前配置复查、风险判断、账户同步、平仓检查不得省略。
4. Main 当前开仓表达式的 `Positions` 来源是 `getTransformPositions()` 的本地仓位镜像和 symbols 联查，不是 runner 中 Binance 账户快照的直接值。模拟也有自己的仓位读取函数。先核对每个字段、类型、账户范围和更新时点，优先在同一轮合并原语义的仓位查询；不得未经验证将实盘账户仓位替换为模拟仓位或反向替换，也不得改变 Positions 中的价格/金额/收益计算和错误语义。
5. 每轮缓存仓位快照只能用于同一账户/同一数据来源、仍有效的评估。开仓、平仓、成交或镜像刷新使结果变化时按现有语义刷新/失效；不能在已发生交易变化后继续用旧快照。对于确实不引用 Positions 的规则，可在保守 AST 分析证明安全后跳过不必要读取，但兼容需要完整环境的调用。
6. FundingRate 已有独立缓存，沿用原逻辑，不增加长期缓存或把不同币种 Funding 数据混合。禁止新增数据库表、修改索引或修改生产 schema；确有必要另行提出证据。

### 必测与验收

- 一轮 1/5/20 个候选的 SQL 调用计数；模拟/实盘分别记录。可复用时重复 symbols 查找及同源仓位查询从逐币 O(N) 降为每轮/每有效快照 O(1)，必要刷新单独计数；模拟平仓索引查找代替重复线性扫描。
- 同一轮切换配置、价格变动、开平仓后仓位变化、行情过期、数据库查询失败、空仓位、币种关闭和不同账户隔离。对比新旧策略环境中实际使用字段，验证信号一致。
- 不减少交易安全必需的账户、订单及配置核实；未启用币种不进入新的开仓候选，已持仓退出仍保持原行为。
- 对新旧策略执行循环使用相同 fixture 与同一行情快照对比，记录查询数、耗时、错误行为及分配量；真实生产 SQL 耗时不在本方案离线验收范围。

## 六、全量验收与交付要求

| 检查 | 要求 |
| --- | --- |
| 业务一致性 | 确定性输入下实盘/模拟各自旧新结果一致；不要求不同交易模式本身变成一致 |
| 性能 | 三阶段分别提供 before/after 原始数据和命中/失效/SQL 计数，不预设未经实测的提升比例 |
| 内存 | 计划和指标缓存容量有界，逐币/逐周期变化、淘汰与异常不能泄漏 |
| 测试 | 相关包 `go test -count=5 -p=2`、关键并发路径 `go test -race`、`go vet`、`go build -p=2 .`、`git diff --check` |
| 回归范围 | `./service/strategy ./feature/strategy/line ./feature ./scanner ./controllers ./service/backtest`，以及受共享代码影响的现货、币本位、监听等实际包 |
| 研究目录 | 全量测试以业务包为准；如 research_specs 存在历史混合包问题，单独报告，不能通过删除历史资料解决 |
| 数据与部署 | 无数据库迁移、无生产写入、无真实订单、无部署；不自动 commit/push |

每阶段交付修改文件、实现说明、测试证据和基准结果；最后复核三阶段联动后的缓存身份、行情时效及账户隔离。保留现有行为的兼容入口，可通过回退代码或原路径验证，不新增 UI 开关或复杂灰度系统。

**最终目标：在不改变任何交易策略和交易行为的前提下，降低重复解析、指标运算及 SQL 开销。实际节省比例以开发后的实测为准。**
